## 二、为"并入 vs 分页"补探的决定性事实（本次新增，原方案未覆盖）

1. **多代理客户（347 家）承载经销收入的 41.0%**——扁平客户视图在结构上无法把这笔钱正确归属到代理商；代理×客户对（树形）是唯一正确表达。用户的钻取直觉有数据硬支撑，不是审美偏好。
2. **直销收入 100% 来自同时走代理的双路径客户（15/16 家，直销侧 24,916 万=直销全部）**——"直销客户"作为客户级分类**在数据中不存在**，直销是纯交易级属性。任何"把客户分成直销/经销两类"的设计都必然是错的；只能做交易/对级分组。
3. **折叠态可浏览性成立**：近12月活跃代理商 160 家（>1000万 20 家、100-1000万 73 家、<10万 34 家合计仅占收入 0.07% 可并入"其他"）；R12 口径代理×客户对仅 2,213 行，注入体积小。
4. **树形 vs 扁平的行数膨胀仅 +15%**（3,685 vs 3,195）——重复行就是多代理客户，属正确表达而非冗余。

## 四、诚实判断：锐评

### 4.1 你的批评是对的，原方案（独立 G 面）应废弃

- "和客户360有什么区别"——答案确实是"没有本质区别"：G 面的 L2/L3 就是 B 面的客户列表+详情换了个入口，两个面共用客户心智模型，必然割裂。
- 更硬的理由在数据侧（§二.1/2）：41% 经销收入只有对级树形能正确表达；直销/经销根本不是客户级属性。独立 G 面同样得面对这两个事实，却把成本花在了新面脚手架上（tab 注册、_tab_names、FACE_META_G、guide 循环四登记点）。
- 原方案的探数与决策点质量仍然有效，本评估全部继承（§一已复核）。

### 4.2 但"整体替换扁平列表"也是错的——你的方案需要一处关键修正

- B 面扁平列表服务的是**高频主流程**："直接找这个客户"（搜索/排序/过滤，3,195 客户）。改成树形强制所有用户先过代理商层，等于为了 160 家代理商的视角惩罚 3,195 家客户的日常查询。
- 过滤器语义会撞车：bTier/bAct/bRisk 是客户级 gold 属性，树形顶层是代理商——"KA 筛选"作用于谁？搜索"比亚迪"命中 12 个代理下的 12 行，展开哪个？
- renderBList 是全看板最承重的函数，整体替换=在最大流量的面上做心脏手术。

### 4.3 推荐方案：B面加「视图切换」，不是替换，也不是新面

```
客户360 顶部工具栏：[按客户 ▾ | 按代理商]   ← 默认"按客户"，现有行为零变化
                                            ↓ 切到"按代理商"
┌ 经销代理（160）──────────────────────────┐
│ ▸ 天午科技      收入X 毛利X 客户228 趋势迷你图 │  ← 折叠=代理商聚合行（F面 fExpandDept 模式）
│ ▾ 另一代理商    ...                         │
│    ├ 终端客户A（此代理口径） 收入 毛利 毛利率     │  ← 展开=对级客户行（缩进子行）
│    └ 终端客户B ...          → 点击进现有客户详情   │  ← L3 复用 renderBDetail，零新组件
├ 直供（37，16 终端客户）─────────────────────┤
│ ▸ 中兴康讯（直供） ...                       │
└─────────────────────────────────────────┘
面包屑从简：单展开 + 展开时列表顶部一条"‹ 返回代理商列表"，不造面包屑组件（YAGNI）
```

- **数据侧纯增量**：新增 `B_AGENTS`（代理商聚合行）+ 对级行数据集（R12 ~2,213 对，体积 <0.5MB 内联）；`B_CUSTS` 一字不动 → golden_diff 存量变量零漂移 by construction，新变量按 F_* 先例登记。
- **灰度**：切换器本身可由 faces.yaml B 面配置项控制显隐（比面级插拔更细一格），默认"按客户"上线，用户零感知。
- **直供呈现（原决策点1）**在新形态下自然落地：顶部两个分组段（经销/直供），比"两组 tab"更顺；直供侧层级塌缩（实体≈终端客户）允许直达详情。
- **多代理重复归属的口径披露**：代理商模式 KPI 与合计按对级口径，面级口径条写明"同一终端客户经多代理拿货时在各代理下分别列示"（v4 措辞规范）。

### 4.4 工程量与风险的诚实估计

| 项 | 独立 G 面（原方案） | 视图切换（推荐） |
|---|---|---|
| Python 数据段 | 代理商聚合（预分组）+ agent_prod.json | 同左（对级聚合同样要做），省新面注册 |
| template JS | 全新面（KPI+排名表+两级 drawer），全是成熟模式 | renderBList 重写（两级行模型）+ 展开态 + openB 适配，**触核心函数** |
| 相对工作量 | 基准 1.0 | ≈1.2-1.4（JS 侧 ~1.5x，Python 侧略省） |
| 生产风险 | 低（隔离） | 中（动 B 面核心；用五门禁+浏览器实测+灰度切换器兜底） |
| UX 结果 | 割裂（你的批评成立） | 依次钻取成立，且保住扁平主流程 |

**结论：可行，工程量不构成暂缓理由。** 真正的风险集中在 renderBList 重写，缓解手段现成（F面展开先例、JS 运行时冒烟门禁、灰度开关）。若施工中 renderBList 重写失控，再退回独立 G 面作为保底——但按取证结果看，不需要。
