## 0. 背景与现状

### 0.1 要解决的问题
写月度报告时"查数"靠手工翻表/Excel 汇总，各类口径的数字分散在多张表与文件中，效率低、易错。
期望以自然语言问答承担 7 类查询：**单点查询 / 排名清单 / 期间对比 / 维度汇总 / 口径类查询 / 趋势 / 实体对比**；
并沉淀为 **查询库**（月度一键重跑）与 **主动体检**（月报前标准检查清单）。

## 1. 目标（MVP，可验收）
1. **本地网页问答**（localhost）：7 类查询全部可用；
2. **报告级答案**：每条答案附 ①口径说明 ②可展开 SQL ③来源表标注 ④结果表格（可复制 Markdown）；
3. **查询库**：任意问答可保存；数据换月后一键重跑，输出同口径数；
4. **主动体检**：一键运行标准检查清单（≥6 类信号），每条可点开 SQL 溯源。

**验收标准（与步骤一一对应）**：
- A. 20 题验收集（用户提供真实问题）：数字与看板/底稿一致率 **≥85%**；不一致项逐条归因（口径 or bug）；
- B. 查询库：换月至新数据后，5 条存量查询重跑结果与人工核对一致；
- C. 体检：≥6 类信号输出，含 SQL 溯源；
- D. 安全：仅 SELECT 白名单、强制 LIMIT、数据不出内网。

## 3. 总体架构

```
┌─ UI: Streamlit（localhost）────────────────────────────────┐
│  聊天 + 结果表格 + SQL 展开 + 口径说明 + 查询库管理页        │
└──────────────┬─────────────────────────────────────────────┘
        ┌──────▼─────────┐
        │  自建管道 (Python)│  问前: 实体替换→口径匹配→schema裁剪→few-shot检索
        │                 │  生成: harness 工具循环 (run_sql / resolve_entity / get_koujing)
        │                 │  执行前: sqlglot AST 白名单校验
        └───┬─────────┬───┘  执行后: 错误回传自修复(≤2) → 合理性检查 → 答案组装
            │         │
   ┌────────▼──┐  ┌───▼─────────────┐
   │ DuckDB    │  │ 内网 vLLM        │
   │ (只读)    │  │ GLM-4.7-PF8     │
   │ qa.duckdb │  │ (tool-calling)  │
   └───────────┘  └─────────────────┘
```

### 3.1 数据层
- `build_db.py`：将 3 个月快照（版本视图 `snap_202606/07/08`）+ silver 4 张 + gold 32 张 + 历史总表装入单个 `qa.duckdb`；
- 应用**只读**打开 + 强制 LIMIT + 长查询中断；`qa.duckdb` 与数据文件不入 git；
- 换月刷新：平台跑批后重跑 `build_db.py --refresh`（幂等，连续两次运行结果一致）。

### 3.2 语义资产（核心投入，决定准确率上限）
1. **口径字典** `semantics\koujing.yaml`：15~20 个指标（收入/毛利/毛利率/数量/ASP/订单数/客户数/新品/环比/同比/累计…），每项含：名称+别名、SQL 表达式、过滤条件、粒度、来源表、口径说明文案、示例问题；
2. **列描述** `semantics\columns.yaml`：67~71 列业务注释（从 DATA_CONTRACT 提取）；
3. **实体别名表** `semantics\entities.csv`：客户/产品规范名+别名（银表自动生成初稿 + 人工维护；解析 = 别名表确定性映射 + rapidfuzz 兜底）；
4. **few-shot 查询库** `library\*.yaml`：问题→SQL→口径标注，检索 top-3~5 注入 prompt（即"查询库"的沉淀本体）。

### 3.3 管道（约 300–500 行 Python）
问前处理 → harness 工具循环 → 校验 → 执行 → 自修复 → 合理性检查 → 答案组装。
工具集：`run_sql(sql)`、`resolve_entity(name)`、`get_koujing(metric)`、`list_tables / describe_table`。
防错细节：prompt 注入"今天=YYYY-MM-DD"；枚举值注入；空结果/量级异常触发二次确认；聚合防 fan-out（先以口径字典固化表达式）。

### 3.4 Harness 选型（调研结论）
- **主选 Pydantic AI**：官方支持 OpenAI 兼容/vLLM、类型安全（适合出数）、与 FastAPI 同源（利于 P5）；**备选 smolagents**（最轻）；
- 排除：LangGraph（过重）、Claude Agent SDK（模型锁死）、Vanna（2026-03 已归档，仅借鉴）、DB-GPT（过重）、WrenAI 完整平台（UI 收费，仅借鉴其语义层 MDL 思路）；
- 兜底：若 tool-calling 解析不稳（GLM 思考+工具混排），降级"结构化 JSON 输出"模式（harness 同样支持）。

### 3.5 UI
- P2：**Streamlit**（本机已装）单文件应用：聊天输入、消息流、结果表、SQL 折叠、口径说明、保存按钮、查询库页；
- P5（可选）：管道封装为 FastAPI 后端 + Tauri 壳加载本地页面（不做 Streamlit-in-WebView）。所有 harness 均为后端库，与本路径兼容。

### 3.6 预期文件结构（落位决策后生效）
```
qa_tool\
├─ build_db.py            # 建库/刷新（幂等）
├─ app.py                 # Streamlit 入口
├─ qa\config.py llm.py agent.py tools.py guard.py pipeline.py library.py
├─ semantics\koujing.yaml columns.yaml entities.csv
├─ library\*.yaml          # 查询库
├─ checks\*.yaml           # 主动体检检查项
└─ README.md
```

## 10. P0 穿刺结果（2026-09-11 已提前执行）

用真实数据（202608 快照 206,900 行）+ 真实模型（GLM-4.7-PF8）+ Pydantic AI 2.42，在 `qa_tool\.venv` 完成四项能力穿刺（脚本：`qa_tool\_probe\probe_agent.py`）：

| 能力 | 实测结果 |
|---|---|
| **工具调用** | ✅ 原生 tool-calling：模型自主调用 `run_sql`，首次 SQL 列名猜错 → 收到错误 → **自动纠正重试**（6.3s 完成） |
| **内容输出** | ✅ 中文答案与地面真值一致：「2026年6月公司总收入 0.74 亿元（73,694,545.62 元）」 |
| **表格输出** | ✅ 结构化输出（output_type）返回 table（8 行 × 2 列），由 UI 层确定性渲染 |
| **图表输出** | ✅ 结构化图表规格（`bar` / x=品类 / y=收入）→ 确定性渲染 SVG；样例：`qa_tool\_probe\sample_output.html`（双击打开） |

结论：harness 选型成立；"错误回传自修复"机制自然生效，将保留进管道设计。
环境隔离：`qa_tool\.venv`（pydantic-ai-slim 2.42 / duckdb 1.5.5 / pandas 3.0.5）；全局 Python 环境保持原样（安装期间对 openai/pydantic 的升级已复原）。

## 附录 A · 外部调研结论摘要（2025–2026）
- **现成方案**：无完全匹配者（DuckDB/parquet + 中文 + vLLM + 单机 + 查询库沉淀）→ 自建轻量管道；Vanna 已归档（借鉴其"问题-SQL 对 RAG"范式）；WrenAI 语义层思路可借鉴（Open-core，UI 收费）；DB-GPT/LangGraph 过重；**Chat2DB 桌面版**可作"零代码先试跑"备选。
- **准确率杠杆（benchmark 佐证）**：few-shot（Tier1 17%→48%）＞ schema 裁剪（表数扩张时全体断崖）＞ 口径字典/语义层（失败模式由"自信错数"变"拒答+澄清"）＞ AST 校验 + 执行错误自修复（≤2 次；只修"不能执行"，不修"逻辑错但能执行"——后者靠口径字典与合理性检查）。
- **实体解析**：别名表（确定性）+ rapidfuzz 兜底；几十~几百实体**不用**向量检索。
- **Harness 对比**：Pydantic AI（官方 VLLMProvider，类型安全）> smolagents（最轻，CodeAgent/ToolCallingAgent）> OpenAI Agents SDK（0.x 变动快）> LlamaIndex（churn）；排除 Claude Agent SDK（模型锁死）、LangGraph（过重）。
- 完整来源链接见调研报告（Vanna GitHub/归档分析、WrenAI 文档、NL2SQL 三框架 benchmark、Text2SQL 生产实践、Google text-to-SQL techniques、Pydantic AI vLLM 文档、smolagents README 等）。
