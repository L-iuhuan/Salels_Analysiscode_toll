## 议题1：存储设计评估（Excel→数据库 / DSE 加密）

### 实测事实（2026-08-24）

| 检查项 | 结果 |
|---|---|
| 当前 ERP Excel 是否被 DSE 加密 | **否——明文**（`data\财务分析-6月(7.6).xlsx` 文件头 `50 4B 03 04`，标准 xlsx） |
| 全量跑耗时结构（764.9s） | Excel 读取仅剩 silver 阶段一次（~20-30s，**占比 <5%**）；看板/KPI 已不读 Excel（批次②/④a 已切 silver） |
| DSE 加密触发条件（本机实测经验） | DSE 只拦截 **Office 白名单进程的写入**；Python 写文件不加密；**读取加密文件需 COM 慢路径** |

### 评估结论

1. **对"耗时太长"：存储不是杠杆。** 每月一次 Excel→DB 导入最多省 20-30s/次（全量跑的 <5%）。耗时主因在计算侧（处理链 ~660s）。若还要提速，杠杆在计算优化或跑批时机（夜间/空闲跑），不在存储。
2. **对"DSE 是实际问题"：真实风险是"数据文件被人用 Excel 打开并保存后被加密"**——一旦发生，calamine 读不了加密件，跑批失败或退回 COM 慢路径。当前文件明文是因为尚未触发；风险是潜在的、随机的。

### 建议方案：快照仓（轻量，不建数据库）

每月 ERP Excel 放入 `data\` 后，由脚本立刻做一次"快照转存"：读一次（若已被加密则走 COM 慢路径）→ 写 **parquet 明文快照**到 `data_warehouse\YYYYMM\`（Python 写入，DSE 不加密）→ 跑批优先读快照，永不碰加密件。
- 收益：DSE 风险彻底隔离；每月数据有不可变快照（可追溯）；读速 1.2-1.6s（已验证）
- 成本：一个 ingest 脚本 + run_all 读侧加快照优先级 + 验收对拍。工作量小
- **不需要 SQLite/DuckDB**：parquet 已是现役格式，零新依赖；远期数据量上台阶再评估

**拍板点 T1**：是否立"快照仓"小批次？（建议：立，优先级中——解决的是 DSE 风险隔离而非速度）

## 议题3：代码→共享盘同步的强制性

### 侦察事实（exp 取证）

- 发布脚本 `kanban\tools\publish_to_share.ps1`：代码 robocopy /MIR 到共享盘 + 写 `version.txt`（git 短哈希）+ 便携 Python 同步 + 可选壳子安装包
- **全靠手动**：无 git hook（只有 sample）、无 CI、无提交后强制步骤；`tools\bump_version.ps1` 里有注册 pre-push 的命令模板但没真注册
- 客户端（Tauri 壳）能发现"代码有新版本"（2 分钟巡检 version.txt），但**开发侧没人知道共享盘是不是过期**；且 version.txt 只判新旧、不判落后几版（漏一次和漏十次看起来一样）
- 共享盘路径**双点硬编码**：发布脚本 + 壳端 `lib.rs:30` 的 `DEFAULT_SHARE_PATH`，改一处不通知另一处就跑偏
- `使用说明.md`（日常入口）完全没提发布纪律

### 建议（分级，可选项）

| 级别 | 措施 | 成本 |
|---|---|---|
| 立即 | ①纪律入台账/宪法：改了 `sales_analytics_platform` 代码，收工必须跑 publish 或在台账登记"未同步"原因；②`使用说明.md` 补发布段落 | 文档级 |
| 轻量 | ③publish 脚本加"本地 HEAD vs 共享盘 version.txt"自检（先检查再同步，并报告落后几版）；④共享盘路径从双点硬编码改为单一配置文件（publish 端读它，壳端发版时核对） | 小工程 |
| 可选 | ⑤git post-commit hook 提醒"代码已改，记得 publish"（提醒非强制） | 小 |

**拍板点 T3**：选哪几条？（建议：①②③④ 全做，⑤ 可选）

## 议题4：看板叙事结构 + 面的插拔与更新节奏

设计师评估结论：
- **叙事线建议**：总览 → 异常与风险 → 客户 → 产品 → 销售 → 行动清单（G面）；tab 顺序微调为 A→G→B→C→D→E→F，F面作为 H1 专项保留
- **插拔与节奏**：`faces.yaml` 作面注册表（`enabled`/`cadence`/`owner`）；单文件模板下主路径=**生成期跳过禁用面的计算与数据注入**（还省耗时），模板条件渲染为辅；不破坏 [STAGE] 协议
- **迁移成本**：tab 顺序变化影响现有用户习惯，建议首次切换时在看板顶部加一行"导航变更说明"挂一个月

**拍板点 T4**：是否接受叙事重排（A→G→B→C→D→E→F）？哪些面要改更新节奏（如 F面 H1 专项改半年/按需）？

## 议题5：子项目与主项目耦合清晰度

### 主干耦合（健康、已文档化）

| 耦合 | 方向 | 状态 |
|---|---|---|
| kanban（Tauri 壳）↔ 平台 | 调用 | "文件级 RPC"：publish 推送→壳 robocopy 拉取→`code\run_chain.py` 执行；**唯一硬契约 [STAGE] 协议**（宪法 R1 保护；壳解析器动态正则，改 total 数不挂但 UI 漂移；壳注释残留早年 5 阶段示例，注释漂移无功能影响） |
| forecasting\unified → 平台 `data\` + sheet "24-26" | 读 | 已文档化，正常 |
| scripts\（freeze/golden_diff/impact_rehearsal） | 工具 | 专绑平台的 QA 工具链，与 forecasting/kanban **零耦合** |
| baseline\ / docs\ | 基线/契约 | 专绑平台；**forecasting 没有自己的基线与契约**（回归靠人工对照，无自动门禁——结构性缺口） |
| _deprecated\ | 封存 | 全仓 0 引用，S7 执行最彻底 |
| CoStrict\ | 无耦合 | **职责完全未文档化**（cache/settings/tasks 目录，建议补 README 说明或 .gitignore 注释） |

### 隐性耦合清单（文档没写但实际存在，按严重性）

| # | 耦合 | 风险 |
|---|---|---|
| C1 | `forecasting\utils\{chart_data,final_forecast,generate_chart_html}.py` 硬编码指向已删除的 `semiconductor_analysis\` | **高：跑必 FileNotFoundError** |
| C2 | `unified` 依赖 `quarterly\output\quarterly_forecast_customer\预测方法排行榜.csv`——README 措辞不精确（真实路径+中文文件名未写明） | **高：quarterly 未跑/路径错位则 unified 启动即崩** |
| C3 | `quarterly\run_quarterly_forecast.py:38` 死引用平台 `shared.data_cleaning`（sys.path 不通，靠内联兜底，平台改了它不跟进） | 中 |
| C4 | quarterly 用 `forecasting\data\`、unified 用 `sales_analytics_platform\data\`——两套数据入口未澄清 | 中 |
| C5 | 根 `tools\bump_version.ps1` 与 `kanban\tools\publish_to_share.ps1` 功能重叠、各管一摊、未交叉引用 | 中（跑错脚本得"只更版本号不更代码"假象） |
| C6 | 共享盘 UNC 双点硬编码（publish + 壳 lib.rs:30） | 中（议题3覆盖） |
| C7-C10 | 安装包手拷无自动化 / impact_rehearsal 隐式 sys.path 依赖 / 人员表提升双端配合 / share-sim 桩协议兼容 | 低 |

### 评估

主项目与 kanban/scripts/baseline/docs 的边界清晰、耦合面少且大部分已文档化。**问题集中在 forecasting 内部（C1-C4）+ 文档化精度**，外加 forecasting 缺基线工具链的结构性缺口（平台有的保障，预测没有）。

**拍板点 T5（扩展）**：forecasting 治理范围——① utils 死路径：修（指平台 output\silver）还是封存；② C2-C4 是否一并修（精确化 README + 死引用清理 + 数据源统一）；③ forecasting 是否补最小基线（复用 scripts\ 模式）。
