## 议题1：存储设计评估（Excel→数据库 / DSE 加密）

### 实测事实（2026-08-24）

| 检查项 | 结果 |
|---|---|
| 当前 ERP Excel 是否被 DSE 加密 | **否——明文**（`data\财务分析-6月(7.6).xlsx` 文件头 `50 4B 03 04`，标准 xlsx） |
| 全量跑耗时结构（764.9s） | Excel 读取仅剩 silver 阶段一次（~20-30s，**占比 <5%**）；看板/KPI 已不读 Excel（批次②/④a 已切 silver） |
| DSE 加密触发条件（本机实测经验） | DSE 只拦截 **Office 白名单进程的写入**；Python 写文件不加密；**读取加密文件需 COM 慢路径** |

### 评估结论

1. **对"耗时太长"：存储不是杠杆。** 每月一次 Excel→DB 导入最多省 20-30s/次（全量跑的 <5%）。耗时主因在计算侧（处理链 ~660s）。若还要提速，杠杆在计算优化或跑批时机（夜间/空闲跑），不在存储。
2. **对"DSE 是实际问题"：真实风险是"数据文件被人用 Excel 打开并保存后被加密"**——一旦发生，calamine 读不了加密件，跑批失败或退回 COM 慢路径。当前文件明文是因为尚未触发；风险是潜在的、随机的。

### 建议方案：快照仓（轻量，不建数据库）

每月 ERP Excel 放入 `data\` 后，由脚本立刻做一次"快照转存"：读一次（若已被加密则走 COM 慢路径）→ 写 **parquet 明文快照**到 `data_warehouse\YYYYMM\`（Python 写入，DSE 不加密）→ 跑批优先读快照，永不碰加密件。
- 收益：DSE 风险彻底隔离；每月数据有不可变快照（可追溯）；读速 1.2-1.6s（已验证）
- 成本：一个 ingest 脚本 + run_all 读侧加快照优先级 + 验收对拍。工作量小
- **不需要 SQLite/DuckDB**：parquet 已是现役格式，零新依赖；远期数据量上台阶再评估

**拍板点 T1**：是否立"快照仓"小批次？（建议：立，优先级中——解决的是 DSE 风险隔离而非速度）

## 议题3：代码→共享盘同步的强制性

### 侦察事实（exp 取证）

- 发布脚本 `kanban\tools\publish_to_share.ps1`：代码 robocopy /MIR 到共享盘 + 写 `version.txt`（git 短哈希）+ 便携 Python 同步 + 可选壳子安装包
- **全靠手动**：无 git hook（只有 sample）、无 CI、无提交后强制步骤；`tools\bump_version.ps1` 里有注册 pre-push 的命令模板但没真注册
- 客户端（Tauri 壳）能发现"代码有新版本"（2 分钟巡检 version.txt），但**开发侧没人知道共享盘是不是过期**；且 version.txt 只判新旧、不判落后几版（漏一次和漏十次看起来一样）
- 共享盘路径**双点硬编码**：发布脚本 + 壳端 `lib.rs:30` 的 `DEFAULT_SHARE_PATH`，改一处不通知另一处就跑偏
- `使用说明.md`（日常入口）完全没提发布纪律

### 建议（分级，可选项）

| 级别 | 措施 | 成本 |
|---|---|---|
| 立即 | ①纪律入台账/宪法：改了 `sales_analytics_platform` 代码，收工必须跑 publish 或在台账登记"未同步"原因；②`使用说明.md` 补发布段落 | 文档级 |
| 轻量 | ③publish 脚本加"本地 HEAD vs 共享盘 version.txt"自检（先检查再同步，并报告落后几版）；④共享盘路径从双点硬编码改为单一配置文件（publish 端读它，壳端发版时核对） | 小工程 |
| 可选 | ⑤git post-commit hook 提醒"代码已改，记得 publish"（提醒非强制） | 小 |

**拍板点 T3**：选哪几条？（建议：①②③④ 全做，⑤ 可选）
