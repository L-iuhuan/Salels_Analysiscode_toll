## 二、方案总体判断

**方案质量高，建议批准，三个口径决策点均建议采纳推荐项（全选 a）。** 依据：

1. **证据驱动**：182 家代理商、3,748 代理×客户对、体积估算（内联 0.5MB / 懒加载 4.6MB）全部来自真实数据只读探查，不是拍脑袋。
2. **零数据侧侵入是正确选择**：代理商聚合放看板段从 silver 行级现算，不建新 silver/gold 表——规避 R3 指纹失效引发的全量重算风险面，也保住灰度上线（visible:false）能力。预分组模式直接吸取了 D 面 241.7s→1.4s 的教训。
3. **交互零发明**：drawer/行点击/跨面跳转/面插拔全部有现成先例，template.html 297KB 单体的改动风险被组件复用压到最低。
4. **渠道类型缺陷拆为独立小工单是对的**——它动 silver 派生列，会触发全量重算与 gold 漂移，且渠道口径变化需业务确认，与看板新面解耦是正确的批次边界。

## 三、施工细化建议（批准后在施工计划中落实）

1. **归属规则配置位置建议改**：方案写 AGENT_ATTRIBUTION 入 `settings.py`。但 settings*.py 哈希是 R3 指纹组成——改归属规则会误触发 silver 全量重算，而归属本质是看板段渲染期聚合规则。建议改放 `faces.yaml`（或 dashboard 侧独立 yaml），迭代归属规则时 `--dashboard-only` 秒级验证即可，不动数据层指纹。
2. **L2 大代理商分页**：天午 228 家终端客户，L2 客户表需显式声明复用 B 面分页模式（bLoadMore，200/页），方案目前只列了先例未点名这一约束。
3. **直供组的层级塌缩**：直供 37 实体仅覆盖 17 个终端客户（实体≈终端客户），三级钻取在直供侧退化为两级。建议直供 tab 允许 L1→L3 直达，避免一层近重复的中转抽屉。
4. **agent_prod.json 缓存一致性**：方案已标记"实施时细化"，建议明确为——该文件写入与 preagg 相同的指纹戳，门禁同时校验两文件，防止"缓存新、明细旧"的错配。
5. **验收门禁补一项**：check_js_runtime 的 Node vm 沙箱覆盖不到 drawer 交互（点击展开/dispose）。第一批验收除五门禁外，加一步浏览器实测（截图核对三级钻取链路），项目在设计轮已有此先例。
6. **新面命名与位置**：遵从 W3 v4"中文面名为主、字母弱化"；tab 位置建议紧随 B 面（代理商与客户视角相邻），叙事顺序 A→R→B→G→C→D→E→F，开工时在施工计划中拍板。
7. **口径条披露空值处理**（决策点 2 选 a 后）：faces.yaml 按 v4 规范写明"销售模式为空的行（约 4.8%）默认按其客户列实体归属"，只写业务含义不写公式。
