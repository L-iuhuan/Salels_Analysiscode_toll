## 一、需求背景与澄清记录

用户原始需求：给生产看板增加两个功能——①增加代理商维度；②客户 top10 产品的详细情况。

两轮澄清后的需求定形：

1. **代理商维度 = 顶层视角逐级钻取**：从代理商（顶层）→ 其下的终端客户 → 对应产品，三级下钻；不是从终端客户反向看单点归属。
2. **代理商归属判定来源 = 「销售模式」字段**（用户明确指定）。
3. 客户→产品 top10 交互钻取（B 面客户360 内点击客户展开其 top10 产品明细）。

**硬约束（用户原话）**：未批准前不准修改现有代码和看板模板，只能从临时目录探索性尝试；项目已上线生产，必须按严格执行措施逐步调整；目标是更新稳定、不中断。

### 2.2 数据模型真相（决定性发现）

**真实业务链路**：

```
拓尔微 ──出货──▶ 通道实体（「客户」列，191 家 = 「代理商/直供名称」列，两列 100% 重叠一一对应）
                      │  其中：代理商 ~182 家（经销） + 直供实体 37 家（直销，仅覆盖 17 个终端客户）
                      ▼
                终端客户（「客户编号」列，3,196 家 = 看板 B 面客户口径 3,143）
                      ▼
                产品（产品品种/型号，多级分类体系现成）
```

- 看板 B 面「客户360」主体 = 终端客户（「客户编号」口径），与「客户」列（通道实体）是**两个不同层级**。
- B 面现有 `ch` 字段（客户级渠道类型，代理 3045/未知 135/直供 16）来自客户全景表独立推导链，健康，未受 silver 行级缺陷影响。

### 2.4 钻取数据可行性（客户→top10 产品）

- `silver_customer_x_product` 现成（客户编号×产品品种×月，含 qty/rev/profit/毛利率/三级产品分类），**零新算**。
- 每客户产品品种数：中位 2、均值 4.9、p90=11、max 280；**Top10 产品收入覆盖率中位 100%**（多数客户产品数<10）。
- 体积估算：全量 3,143 客户×top10×6 字段 ≈ +2.2MB（b_data.js 现 6.09MB）；拆独立 json 懒加载可化解（b_trend.json 1.12MB 先例）。
- 代理商→客户→产品三级全量注入 ≈ 4.6MB；仅 KA+KM 客户 ≈ 0.3MB。

### 2.6 顺带发现的生产缺陷（与本次需求无依赖关系）

- silver 行级「渠道类型」派生列当前**全部为"未知"**（DATA_CONTRACT 声称 100% 填充代理/直供）。疑似根因：销售模式列 105 个唯一值（含 103 个公司名脏值+NaN）未按语义归一即做映射。影响面仅行级渠道切分，不影响看板现有显示。建议独立小工单修复（见 §6）。

## 三、方案设计

### 3.1 主体：新增「代理商面」（face_id 建议 G，面名"代理商"）

三级钻取结构：

```
L1 代理商总览与列表
   ├ KPI 卡：代理商数 / 代理侧收入·毛利·毛利率 / 覆盖终端客户数 / 直供侧对照
   ├ 排名表（可排序）：代理商 | 收入 | 毛利 | 毛利率 | 终端客户数 | 产品数 | 近12月趋势迷你图 | 环比
   │   （口径：非直销行聚合；行级归属，见 §4 决策点3）
   └ 点击行 →
L2 drawer：该代理商下的终端客户列表
   ├ 头部：代理商摘要（收入/毛利/客户数/月度趋势小图）
   ├ 客户表：终端客户 | 此代理口径收入 | 毛利 | 毛利率 | 产品数 | 客户类别(KA/KM/MM)
   │   （多代理客户在此只显示该对组合的数据）
   └ 点击行 →
L3 drawer：该客户在此代理商下的 top10 产品明细
   └ 产品表：品种 | 数量 | 收入 | 毛利 | 毛利率 | 收入占比；配占比条形图
```

- **数据侧零侵入**：不建新 silver/gold 表、不改现有表结构；代理商聚合在 generate_dashboard 看板段从 silver 行级现算 + 预分组（`_REX_BY_YM` 模式，规避 D 面曾 241.7s 的全表扫描坑）。
- **归属规则配置化**：入 `settings.py`（AGENT_ATTRIBUTION 规则键：销售模式→归属映射表），faces.yaml 口径条同步写明，不写死代码。
- **体积控制**：L1+L2 数据内联（182 行 + 3,748 对，≈0.5MB）；L3 产品明细拆独立 `agent_prod.json` 懒加载（全量 ≈4.6MB，生成物不占 b_data.js）。
- **直供呈现**：按 §4 决策点 1 的拍板结果实施（两组 tab / 仅代理商 / 直供对照卡）。

### 3.2 配套：B 面客户360 增强（第二批）

- renderBDetail 的"Top5 产品品名"位置改造：点击展开 drawer 显示 top10 产品明细（品种/数量/收入/毛利/毛利率/占比）——**复用第一批 L3 渲染组件**。
- 客户详情新增"经过的代理商"小节：该终端客户通过哪些代理商拿货（348 家多代理客户在此有增量价值；单代理客户显示唯一归属）。

### 3.3 暂缓项：各面全面渠道切分

- 接触点 12+ 处（约为第一批 4 倍成本）；且 95.3% 客户走代理渠道，二元切分一边倒，分析价值存疑。
- 若未来要做：前置依赖 §2.6 渠道类型缺陷修复；E 面 e_decomp 加 `("agent","渠道","_ch",None)` 元组是最便宜单点切分（generate_dashboard.py:1917-1921），可作为试点。

## 六、不中断生产的保障路径（贯穿全程）

1. **分支隔离**：iter 分支开发，master 不动，验收门禁全绿才合入（项目既有纪律，单批单分支）。
2. **灰度上线**：faces.yaml `visible:false` 隐形上线 → `--dashboard-only` 秒级重渲染验证 → 人工确认后翻开（F 面成熟先例，生产用户零感知）。
3. **数据侧零侵入**：不动 silver/gold 现有表结构，不触发 R3 指纹全量重算风险面；新计算全部在看板段。
4. **模板迭代不中断**：`--dashboard-only` ~1s 快速验证模板改动，无需全量跑批。
5. **发布合规（S9）**：`agent_prod.json` 为生成物不上盘（dashboard\data\ 下生成 js 同类，白名单外即不上盘，客户端跑批自生成）；无新增源文件则无需改白名单。
6. **回退双保险**：git revert 单点回退 + visible 开关秒级隐藏新面。
7. **客户端无感**：看板产物在 output\（同步树外，r23 保障）；新代码经共享盘白名单自然分发，客户端首跑 R3 指纹校验自动全量重算保障正确性。
