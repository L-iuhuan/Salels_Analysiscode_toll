## 一、总体结论

项目已经从原始 semiconductor_analysis 成功精简为一个可携带的“前段处理 + 后段看板”流水线，链路设计（silver → product → customer → kpi → cross_ref → dashboard）总体成立，S1+S2 的 Excel 读取优化也是有效的。

但目前存在三类问题：

1. **会造成“结果错误但程序不报错”的逻辑问题**：最严重的是 Silver 缓存不校验输入文件变化、统一 Silver 绕过了各阶段的清洗口径、看板存在大量 2024/2025/2026 硬编码和列位硬编码。
2. **会让流程在特定条件下崩溃的可靠性问题**：依赖清单缺 xlsxwriter、客户报告写入存在 UnboundLocalError 隐患、产品历史画像关闭时变量未初始化、pandas 3.x category dtype 兼容性问题等。
3. **剩余性能瓶颈**：前段客户画像/Gold 层、后段看板 6 个面仍存在大量 O(客户数 × 原始行数) 级别的 Python 循环；交叉销售被重复计算两遍；Silver 聚合中有一个明显的 O(分组数 × 明细行数) lambda。

修复顺序建议：**先保证输入变化会重算 → 再统一清洗口径 → 再消除看板硬编码 → 最后做向量化性能优化。**

## 二、运行链路与依赖关系

### 2.1 实际链路

```text
run_chain.py
  ├─ 定位 data/ 最新 xlsx
  ├─ 创建 processing/output -> 包根 output 的目录联接
  ├─ 子进程 processing/run_all.py
  │     ├─ silver    读 Excel → 清洗 → 3张silver CSV + silver_cleaned_rows.csv
  │     ├─ product   读 silver_cleaned_rows.csv → 产品报告Excel + gold_product_portrait.csv
  │     ├─ customer  读 silver CSV + raw属性 → 客户全景 → 20+张gold CSV + 客户报告
  │     ├─ kpi       重新读Excel → gold_kpi_daily.csv
  │     └─ cross_ref 读gold → cross_*.csv
  └─ 子进程 dashboard/generate_dashboard.py
```

| 下游 | 上游依赖 | 缺失时的行为 |

## 三、P0 级问题：会直接导致结果错误

### P0-1：Silver 缓存不校验源文件变化，换新 Excel 后仍用旧结果 ★最严重

**位置**：`processing/run_all.py:78-116`、`128-149`

`_silver_cache_valid()` 只对 `config/settings.py` 和 `shared/data_cleaning.py` 的内容做 SHA256，**完全没有包含输入 Excel 的路径、修改时间、大小或内容哈希**，也没有包含 `settings_customer.py / settings_product.py`。

实际后果：用户按 README 放入 7 月新 Excel 后运行 `python run_chain.py`，只要 `output/silver/*.csv` 还在，阶段日志会显示：

```text
Silver层缓存有效，跳过
```

随后 product、customer、dashboard 全部基于上个月的旧 silver 继续计算。**程序正常退出，看板却是旧数据。** 在隔离副本中替换 Excel 内容后复跑，确认 100% 复现此行为。

**建议**：

- 缓存指纹 = 源文件 `路径 + mtime + size + 内容哈希` + 所有影响 silver 的配置（settings.py、settings_customer.py、settings_product.py、ERP_COL_MAP、清洗函数源码）。
- 新 Excel 与旧 Excel 指纹不同时自动失效，无需用户加 `--force-silver`。
- README 明确“换数据后第一次会自动重算”。

---

### P0-2：统一 Silver 绕过了各阶段清洗口径，产品/客户结果在链路模式下与单模块模式不一致

**位置**：`processing/run_all.py:158-211` vs `processing/shared/data_cleaning.py:305-430` vs `processing/product_lifecycle/run.py:211-258`

正常链路中，`stage_silver()` 是直接读 Excel → `rename` → `monthly_aggregate_double_pass`，并没有经过 `build_silver_layer()` 中的以下逻辑：

- 客户分析要求的 `start_date = 2024-01-01` 窗口过滤：**未执行**
- 最新不完整月检测（`incomplete_month_threshold_day=25`）：**未执行**
- 产品分析要求的负/零销量剔除、毛利率钳制、`data_start_date` 过滤：**未执行**

而 `stage_product(skip_silver=True)` 和 `stage_customer(skip_silver=True)` 会直接使用这个“口径不全”的 silver。结果是：

- 链式运行与单独运行 `customer_analysis/run_pipeline.py` 或 `product_lifecycle/run.py` 的数值可能不同。
- 客户分析可能把 2024 年前数据纳入统计。
- 当月未关账数据可能被当成完整月参与 KPI/趋势。
- 产品分析在链式运行时没有做产品口径的 Winsor 裁剪。

**建议**：这是典型的“共享层 vs 阶段专用层”设计冲突。要么让 silver 统一为全量、未裁剪的“基础事实层”，由 product/customer 各自再做窗口过滤；要么在 stage_silver 中显式应用两套口径并分别落盘。**不要继续让 stage_silver 和 build_silver_layer 走两条不同清洗路径。**

---

### P0-3：看板大量硬编码 2024/2025/2026 和固定列位置，过了 2026 会静默出错

**位置**：`dashboard/generate_dashboard.py:350-379`、`462-493`、`1688-1689`、`1798-1800`、`1838`；`dashboard/template.html:1760`、`2091-2201`

具体问题：

| 硬编码 | 后果 |
|---|---|
| `sheet_name="24-26"` 在前后端各写死 | sheet 改名后直接失败 |
| `sales_col_raw = raw_all_cols[4]` | 列顺序一变，销售员列会静默变成别的列 |
| `pline_new_col = raw_all_cols[24]`、`newprod_col = raw_all_cols[28]` | 同上 |
| `cat_col` 回退 `raw_all_cols[66]` | 同上 |
| `yd(2024/2025/2026)`、模板 `TREND.r26/r25` | 2027 年看板 KPI 全部失效或为空 |
| 模板 JS `keys2026`、`keys2025` | 同上 |
| `_h1_periods` 固定 25h1/25h2/26h1 | 2027 年后 F 面产品 H1 对比失真 |
| 客户归因中硬编码 `"2026-01-01" ~ "2026-06-30"` | 同上 |

隔离副本中把销售员列挪到不同位置后，看板生成成功，但 D 面把“利润”列当成了销售员，凭空生成了 130 个“销售员”。**说明目前没有任何列位置校验，错了也不会报错。**

**建议**：

- 所有列改为按语义名匹配，并加“必须存在”断言：`实际业务员`、`型号_产品线（新）`、`是否新品`、`产品品类（新）`。
- 年份全部从 `_latest_period` 推导，模板中的年份 schema 改为动态传入。
- sheet 名从统一配置读取或自动识别包含明细数据的 sheet。

### P0-4：F 面“新品分析”用了产品线粒度而不是 SKU 粒度

**位置**：`dashboard/generate_dashboard.py:1642-1645`

```python
_new_prods = rex[rex["_is_new"]]["_prod"].unique()
for _prod in _new_prods:
    _pdata = rex[rex["_prod"] == _prod]
```

`_prod` 实际是“产品线”，而正确的产品粒度列是 `_item`（存货名称/SKU）。用历史 output 验证：

- `F_PRODUCT_LIST` 有 426 个 SKU；
- `F_NP_ANALYSIS` 只有 9 条“产品线”，且 `survival` 出现 **108.3%** 这种不可能值。

这会导致 F 面新品数量、存活率、新品收入全部错误。**建议改为 `_item`**，并限制 survival 到 0–100%。

### P0-5：依赖清单缺 xlsxwriter，且自动安装路径错误

**位置**：`requirements.txt`、`processing/reports/gold_exporter.py:113`、`processing/run_all.py:300-320`

- `requirements.txt` 没有 `xlsxwriter`，但客户报告生成器运行时 `import xlsxwriter`。新电脑按 README 装完依赖后，客户阶段会在最后写 Excel 时崩溃。
- `run_all.py` 的自动安装路径是 `processing/requirements.txt`，但实际文件在包根目录。自动安装失败会被 catch 后仅打印警告，用户很难发现。

**建议**：requirements 增加 `xlsxwriter`；自动安装路径改为包根；自动安装失败应阻止运行或给出明确修复命令。

---

### P0-6：pandas 3.x category dtype 兼容性不足

**位置**：`processing/shared/data_cleaning.py:254-282`、`processing/analysis/pricing/pricing_actions.py:37-57`

`requirements.txt` 写的是 `pandas>=2.2` 且没有上限，当前环境已经是 pandas 3.0。Silver 读取时把 `客户编号`、`产品品种` 设为 `category`，某些函数在 category 键上做 `groupby + map` 后，数值列会被 pandas 3 错误地传播成 category，随后做除法时报：

```text
TypeError: Object with dtype category cannot perform the numpy op divide
```

隔离副本中在 `calc_markup_opportunity()` 的 `客户销量占比` 计算处复现了此错误；实际数据是否触发取决于类别结构与 pandas 版本，风险很高。

**建议**：

- 短期：`pandas>=2.2,<3.0` 锁版本。
- 中期：在函数入口对分组键统一 `astype(str)`，或放弃 silver CSV 的 category dtype，改用时再转换。

## 四、P1 级问题：链路正确性与健壮性

### 4.1 数据验证顺序错误，V1 检查永远误报

**位置**：`processing/run_all.py:155-161`

`validate_raw(raw)` 在 `rename_erp_columns(raw)` **之前**执行，而验证器检查的是标准列名（客户编号、产品品种……）。所以每次运行都会打出“缺少客户编号/产品品种/数量/金额”的告警，但检查实际没有意义。

另外 `validate_clean`/`validate_silver` 对数量和 `qty_sum` 检查 `>=0`，与“保留负销量/退货红冲自然冲减”的业务规则自相矛盾，退货月会持续误报。

---

### 4.2 产品历史画像关闭时直接崩溃

**位置**：`processing/product_lifecycle/run.py:331-355`、`447-455`

当 `hist_portrait_enabled=0` 或 `hist_portrait_points` 为空时，`hist_sheet_df` 不会被初始化，但后面 `write_excel_report(..., hist_sheet_df, ...)` 仍会引用它，触发 `UnboundLocalError`。隔离副本已复现。

---

### 4.3 客户报告 Excel 写入存在 UnboundLocalError 隐患

**位置**：`processing/reports/gold_exporter.py:156-174`

`col_len` 只在数值分支和字符串分支赋值；如果某列第一行是 `NaN` 或 list/ndarray，执行到 `max(max_len, col_len)` 时变量未定义。用最小 gold 表复现了崩溃。当前实际数据可能碰巧没有触发，但换一个月/换客户后随时可能触发。

---

### 4.4 cross_ref 的“产品客户群健康度”实际是空转

**位置**：`processing/cross_reference/run_cross_ref.py:108-139`

它查找 `RFMπ_层级` 和 `风险等级`，但客户全景表已经删除了 `RFMπ_层级`，且真实列名是 `风险评级` 而不是 `风险等级`。于是 `merge_cols` 只有“客户编号”，函数最后返回空 DataFrame。

历史 output 验证：`cross_product_customer_health.csv` 只有 852 行、3 列，应有的“高风险客户数”等字段从未生成。**建议修正列名匹配，或者确认该表不再需要后正式下线。**

---

### 4.5 F 面人员映射漏掉“营销中心（中心直属）”4 人

**位置**：`dashboard/generate_dashboard.py:1462`

正则：

```python
r'###\s+\d+\.\d+\s+(.+?)（\d+\s*人'
```

无法匹配 `### 3.1 营销中心（中心直属，4 人）`，因为括号后不是直接数字。测试结果：md 中共 73 人，只映射到 69 人，3.1 节 4 人全部被标记成“已离职”。建议改为匹配行尾的人数，例如放宽为 `.*?（\d+\s*人` 或直接解析 `（(\d+)\s*人`。

另外，所有未匹配销售员一律标“已离职”也不严谨，应区分“人员表未维护”和“确已离职”。

---

### 4.6 阶段失败不总是阻断流程，run_chain 可能拿到 exit=0

`run_all.py` 中 product/customer/cross_ref 阶段失败时大多只打印“未产生完整输出”并继续，最后仍以 0 退出。`run_chain` 只检查 returncode，因此可能出现“前端实际缺表，但继续生成看板并在 dashboard 处才崩溃”的情况。

建议每个 stage 返回结构化结果，缺关键产物时 run_all 返回非 0，或 run_chain 做产物清单校验。

---

### 4.7 看板前置校验不足，`--skip-processing` 没有真正跳过所有处理

`generate_dashboard.py` 直接 `pd.read_csv` 多个 gold 文件，没有“产物清单”预检。部分 output 缺失时错误信息不友好。

同时 `--skip-processing` 仍会重新读取原始 Excel 的 13 列并在 6 个面做大量重算，因此所谓 skip 只省了前段 287 秒，后段 213 秒仍全量执行。

---

### 4.8 无真实库龄数据时的“估算值”被当作真实结果展示

`get_inventory_aging()` 在没有库龄和 BOM 文件时，会用“近3月销量 × 2”估算库存并人为划分库龄结构。随后：

- 异常检测会基于这些估算值产生“库存呆滞/长库龄积压”告警；
- 看板中没有明确区分“估算”和“真实”。

这属于业务误导风险。建议保留估算但给所有派生表加“数据来源=估算”字段，并在看板显著位置标注，或当无真实数据时关闭库存类告警。

---

### 4.9 正负销量业务规则不统一

- `shared/data_cleaning.py` 当前“保留负销量”；
- `product_lifecycle/run.py:_prepare_data` 却剔除 `数量<=0`；
- dashboard 原始数据路径也没有过滤负销量。

三处口径不一致，导致产品分析、客户分析、看板 KPI 对退货/红冲的处理结果可能互相打架。建议在配置中定义唯一规则，所有链路共用。

---

### 4.10 其他小问题

- `Isolation Forest` 检测器从未被调用：`b2b_v2/anomaly/run.py` 只是 import 了它。
- `core/pipeline.py` 的 `--pipeline` 模式是残缺的：product 阶段传入的 df 没有 `_月` 列会 KeyError，silver 也不落盘；建议修复或从 CLI 移除。
- `run_all.py` 直跑时 `find_source_data()` 取目录第一个 xlsx，而不是最新；与 run_chain 的最新文件逻辑不一致。
- `dashboard/generate_dashboard.py` 的 42 个 `%%KPI_*%%` 替换键中，模板里实际只有 2 个占位符，其余替换全是死代码；前端 KPI 实际从 TREND/E_MONTHLY_KPI 重算。
- “Raw=Silver验证”审计项是拿一个不会出现的字符串做检查，历史报告也承认它必然 FAIL，属于无效审计。
- `pricing_customer.py`、`pricing_lifecycle.py` 等存在 return 之后的残留重复代码和大量未使用 import，维护成本高。

## 五、性能瓶颈诊断

### 5.1 历史基线（来自 docs 效率报告）

| 阶段 | 原耗时 | 说明 |
|---|---|---|
| silver | 31.0s | 读 219.7MB Excel + 聚合 + 写 184MB CSV |
| product | ~45s | 含 12 个历史画像点多进程 |
| customer | 203.5s | 画像 63.4s + Gold 123.6s + 报告 15.9s |
| kpi + cross_ref | ~8s | |
| 后段看板 | 272.8s → 213.2s | S1/S2 优化后 |
| 端到端 | 560.4s → 约500s | |

### 5.2 核心瓶颈：大量 O(C×N) Python 层扫描

#### 前段

1. **`monthly_aggregate_double_pass` 的 avg_price lambda**  
   `processing/shared/data_cleaning.py:215`：

   ```python
   "avg_price": (rev_col, lambda x: x.sum() / df.loc[x.index, qty_col].sum() ...)
   ```

   每个“产品×月份”分组都回原 DataFrame 按 index 查找一次。实际数据约 818 个产品 × 30 个月 ≈ 2.4 万个分组，每个分组扫 19 万行明细，复杂度约 O(分组数 × 总行数)。应改为先 groupby 求和，再向量化相除。

2. **客户画像逐客户扫描全表**  
   `processing/customer_analysis/portrait.py:455-467`：

   ```python
   for cid in customers:
       c_mask = cust_monthly["客户编号"] == cid
       cp_mask = cust_prod["客户编号"] == cid
   ```

   3143 个客户 × 每次全列比较；`_derive_channel` 还逐客户扫原始数据。这是文档中 63.4s 的主要来源。应预 groupby 或 map。

3. **Gold 层交叉销售被完整计算两次**  
   `processing/b2b_v2/actions/run.py:21` 和 `:44` 两次调用 `generate_cross_sell()`。而 `cross_sell.py` 本身是三层嵌套循环：客户 × 未购产品 × 已购产品，且每个产品还要反查产品画像和库龄表。实际数据 3143 客户 × 818 SKU，这个规模会非常昂贵。应只算一次，并改为向量化/集合索引。

4. **旅程分类、波动性、真实利润、异常规则大量 iterrows/重复 groupby**  
   `stage_classifier.py` 主循环后为排名又重复 groupby 多遍；`true_profit_estimator.py` 和 `anomaly/rules.py` 大量 `iterrows`；`rules_engine.py` 用 `df.apply(axis=1)`，L1 告警又在客户循环内过滤全表。

#### 后段

5. **dashboard 6 个面到处重复过滤 `rex`**  
   典型模式：

   ```python
   for cid in all_custs:
       cm = cust_mo[cust_mo["_cust"] == cid]
   ```

   出现于：

   - B 面客户趋势/财务：`generate_dashboard.py:618-644`
   - KA/AA 产品变迁历史：`:665-724`（客户数 × 月数 × 全表）
   - 客户同比/品种下降诊断：`:1048-1061`
   - E 面月度 KPI/拆解：`:1223-1400`
   - F 面产品趋势/Top5/品类映射：`:1839-1905`
   - 客户热力图：销售员 × Top33 客户 × 全表过滤

   以 3143 客户、30 个月、19 万行计算，仅“每客户每表过滤一次”就是上亿次比较；而实际有十几个这样的循环。这是后段 170s 计算时间的根本原因。

6. **CSV 层间交换又大又慢**  
   `silver_cleaned_rows.csv` 184MB 一写多读，丢 dtype 且需要重新解析。建议改为 Parquet/Feather，或按第 9 节评估 SQLite。

7. **产品历史画像多进程任务传全量 DataFrame**  
   `product_lifecycle/run.py` 对 12 个历史点每个都提交一份完整 `df_hist` 和 `prod_month_all` 给进程池，内存峰值高、序列化开销大。建议降低默认历史点数（如 3/6/12），或改为共享内存/先落盘再并行读取。

### 5.3 性能优化优先级

| 优化项 | 预计收益 | 风险 |
|---|---|---|
| 修复 silver avg_price lambda | 数十秒，内存下降 | 低 |
| 客户画像向量化 | 可能从 63s 降至 10s 级 | 中，需数字回归 |
| 交叉销售只算一次 + 集合索引 | Gold 层可能省 60–100s | 中 |
| dashboard 预聚合 + groupby dict/merge 替代循环 | 后段可能省 100–150s | 中高，需回归 |
| silver/gold 改 Parquet 或 SQLite 分层存储 | 10–30s + 省盘 | 低-中 |
| 后段只读 gold、不再重算 raw | 15–90s | 高，架构改动 |
| 6 个面并行 | 可缩短后段一半以上 | 中高 |

## 六、架构、依赖与可维护性问题

### 6.1 输出目录依赖 Windows 目录联接

前端部分模块路径指向包根 `output/`，另一部分写死 `processing/output/`，靠 `run_chain.py` 创建 junction 统一。它能工作，但：

`run_all.py` 是实际入口，`core/pipeline.py` 是依赖注入容器，但 Pipeline 模式不完整且无人使用。这增加了理解成本，建议二选一。

- `analysis/b2b_adapters.py`、`analysis/c6_production_mapping.py`、`customer_analysis/customer_master.py` 等实际上没有被默认链路 import；
- `customer_analysis/models.py`、`scoring.py` 只是转发包装；
- 多个 pricing 文件有 return 之后的残留代码；
- `matplotlib`、`rapidfuzz`、`scikit-learn` 在当前实际链路中几乎没有被使用（IF 未启用，rapidfuzz 只在未启用的 customer_master 中）。

### 6.4 没有测试与回归基线

精简包中没有测试目录。对于一个“数字不能变”的分析项目，后续任何性能优化都必须先冻结当前 output/HTML 作为回归基准。原始项目有历史 GOOD 文件，但精简包没有携带任何自动校验。

## 九、SQLite 替代 CSV 专题分析

### 9.1 结论先行

**“不用 CSV，改用 SQLite 本地文件”是可行的，而且 SQLite 是 Python 标准库自带的零安装方案；但如果只是把 `to_csv/read_csv` 机械替换成 `to_sql/read_sql`，收益不会特别明显。真正的大幅提速来自“把重复过滤和聚合下推到 SQL/索引”，而不是文件格式本身。**

原因：

- 当前端到端约 500 秒里，CSV I/O 大约只占 10–30 秒，大头是 Python 循环计算和 Excel 读取。
- 当前明细数据只有 19 万行左右，并不算大；CSV 的主要痛点是“重复全量解析 + 丢 dtype + 无法按需取列”。
- SQLite 对“按客户编号/月份/产品品种做选择性查询”非常合适，能天然替代 dashboard 里大量 `df[df["_cust"] == cid]` 循环。
- 但 SQLite 对 pandas 全表分析（需要把整列读回内存做统计）不一定比 CSV 快，甚至可能略慢。

### 9.2 实测数据

测试对象：历史实际输出 `silver_cleaned_rows.csv`（180.8MB，191,725 行 × 71 列）。测试环境为隔离 venv，未改动原项目。

| 操作 | CSV | SQLite | Parquet（pyarrow） |
|---|---|---|---|
| 全量写盘 | 6.0s | 3.25s | 0.86s |
| 全量读盘 | 5.5–7.3s | 6.0s | 0.18s |
| 只读 6 个业务列 | 2.89s | 0.50s | 0.02s |
| 查询单个客户（带索引） | 需先全量解析后过滤 | 0.6–6ms | — |
| 按客户聚合全部客户 | 15ms（内存中 groupby） | 180ms | — |
| 落盘体积 | 180.8MB | 197–201MB（含索引） | 15.2MB |

结论：

- **SQLite 写盘快于 CSV，选择性读列明显快于 CSV**；适合做“明细仓库”。
- **SQLite 全量读回 pandas 并不比 CSV 快多少**，所以 product/customer 中“整表拉回内存做统计”的场景不能指望换 SQLite 大幅提速。
- **pandas 数据已在内存时，groupby 比 SQLite 更快**（本数据规模下 15ms vs 180ms）。真正的问题是代码反复全表扫描，而不是存储格式。
- **Parquet 在“整表读写”场景下是碾压级优势**，但需要安装 pyarrow，不符合“零安装 SQLite”的约束。

### 9.3 为什么 SQLite 不是银弹

1. 当前 CSV 只在阶段边界写读一两次，I/O 占比不高。只换格式预计端到端省 5–15 秒，用户体感不明显。
2. SQLite 存储 71 列明细后体积约 197MB，比 CSV 还略大；索引会再增加体积。
3. 中文列名、Period/日期、float32/category dtype 需要额外 schema 管理。
4. `pandas.to_sql` 对极宽表、极多小表的写入管理比较繁琐，需要统一封装。
5. 若 dashboard 继续“全量读回 DataFrame 再 Python 循环”，SQLite 无法解决瓶颈。

### 9.4 SQLite 正确用法

如果要上 SQLite，建议按下面方式改造，而不是简单替换文件后缀：

```text
output/
  pipeline.db          # 单一本地数据库，替代 output/silver/*.csv 与 output/gold/*.csv
  report/              # Excel 报告仍然保留，给人看
  export/              # 可选：自动导出 gold CSV，给 Excel/BI 用户
```

建表和索引建议：

| 表 | 关键索引 |
|---|---|
| silver_rows | `(客户编号)`、`(产品品种)`、`(发货日期)`、`(客户编号, 发货日期)`、`(产品品种, 发货日期)` |
| customer_monthly | `(客户编号, _月)` |
| product_monthly | `(产品品种, _月)` |
| customer_x_product | `(客户编号, 产品品种, _月)` |
| 客户全景/产品画像等 gold 表 | 主键客户/产品，按需加业务负责人、客户层级等索引 |

改造模式：

1. **前段写完 DataFrame 后直接 `df.to_sql(..., if_exists="replace")`**，替代 `to_csv`。
2. **dashboard 中所有 `rex[rex["_cust"] == cid]` 改为按索引的 SQL 查询**，或更推荐的做法：一次 `GROUP BY` 把“客户 × 月 / 客户 × 产品 / 销售员 × 月”等中间聚合查出来，替代 Python 循环。
3. **只 SELECT 需要的列**。例如 B 面只需要 6 列，就不要读 71 列。
4. **保留 pandas 做复杂统计模型**（趋势、评分、ETS 预测等），SQLite 只负责存取和关系过滤，不要试图把所有逻辑写成 SQL。

按这个方式，收益来自两部分：

- 消除重复全量 CSV 解析：约省 10–20 秒。
- 消除 dashboard 的重复 DataFrame 过滤循环：可能省 50–120 秒（与第 5 节的向量化方案重叠）。

### 9.5 SQLite 与其他方案的对比

| 方案 | 是否零安装 | 全量读写 | 选择性查询 | 磁盘占用 | 适用场景 |
|---|---|---|---|---|---|
| CSV | 是 | 慢 | 差 | 中 | 当前，简单通用 |
| SQLite | **是（Python 自带）** | 中 | 好（需索引） | 中-大 | 明细仓库 + 按客户/产品查询 |
| Parquet | 否（需 pyarrow） | 非常快 | 好 | 小（约 1/10） | 阶段间全量交换、pandas 分析 |
| Feather/Arrow IPC | 否（需 pyarrow） | 非常快 | 中 | 小-中 | 单机临时交换 |
| DuckDB | 否（需 duckdb） | 快 | 非常好 | 小 | SQL 分析 + Parquet，长期最佳候选 |

### 9.6 最终建议

1. **如果坚持“不额外安装任何东西”**：用 SQLite 是合理选择，但必须同时把 dashboard 的重复过滤改成索引查询/一次 groupby，否则收益不大。建议先做一个小范围试点：把 `silver_cleaned_rows` 和 `customer_x_product` 放进 `pipeline.db`，看板 B/E/F 面的热点查询改 SQL，实测端到端时间。
2. **如果可以接受安装 pyarrow**：建议明细层用 Parquet（`silver_rows.parquet`），维度表和 gold 表用 SQLite 或继续 CSV；这样全量读写和磁盘占用收益最明显。
3. **长期最优**：引入 DuckDB，直接查询 Parquet/CSV/SQLite，SQL 下推聚合，兼顾分析性能和零服务部署；但这是更大的架构调整，不建议在第一轮就上。
4. **无论用哪种存储，业务用户仍需要 CSV/Excel 出口**。README 承诺“output/gold 里的 CSV 可以用 Excel 打开”，迁移后应保留自动导出功能。

## 最后判断

这个精简包的方向是对的：单一输入、单一输出、便携运行、普通用户只需一条命令。当前最大风险不是速度，而是：

1. **“输入换了但结果还是旧的”**；
2. **“清洗口径在链式与单模块模式不一致”**；
3. **“看板被 2026 年写死”**；
4. **“部分字段看起来有值，实际是估算值或错误粒度”**。

建议先把这四类正确性问题修掉，再按性能路线图做向量化；每改一步都用实际输出做数字回归，避免“快了但数字变了”。SQLite 可以作为中间存储升级的一部分，但必须和查询模式改造一起做，单独换格式不会带来质变。

## 补充定稿：Parquet + DuckDB 实测方案与落地设计

> 本部分为 2026-08-15 实测后补充，代表后续推荐的最终技术路线。

### 1. 最终结论

经过真实数据实测，确定后续技术路线为：

```text
Parquet 负责存储和归档
DuckDB 负责 SQL 聚合与看板预聚合
pandas 只负责评分、预测、规则等复杂算法
看板默认只读最终缓存表
```

**不再以 CSV 作为主存储和阶段交换格式。**

CSV 仅保留两种用途：

1. 需要核对结果和逻辑时，按需导出；
2. 业务用户需要 Excel/CSV 文件时，按需导出。

---

### 2. 实测结果

测试数据为真实历史文件 `财务分析-6月（7.6）.xlsx`：

- Sheet：`24-26`
- 明细：191,725 行 × 67 列

| 测试项 | CSV / 原方案 | Parquet / DuckDB |
|---|---:|---:|
| 明细落盘耗时 | 8.15s | **0.77s** |
| 明细文件体积 | 172.3MB | **15.2MB** |
| silver 三张聚合表耗时 | 6.84s | **合计约 0.24s** |
| 看板式读取 6–13 列 | 1.4–2.3s | **0.09–0.16s** |
| 看板式逐客户过滤 3143 次 | 7.5s | 改为一次 SQL：**0.03–0.1s** |
| 客户层级 × 产品线聚合 | — | **0.04s** |
| 建 DuckDB 原生表 | — | 2.46s，27.3MB |

说明：

- Excel COM 读取耗时未能在当前环境实测，需要在公司 Windows 电脑上补测。
- 未加密 Excel 的 calamine 读取实测约 25.8s，该部分仅作为参照，不代表亿赛通环境。
- Parquet 读回 pandas 后如果继续使用原“逐客户布尔过滤”循环，实测反而可能变慢；必须改成 DuckDB SQL 聚合或 pandas 一次 groupby。

---

### 3. 与 calamine 的关系

**采用新方案后，主链路不再需要 calamine。**

原因：

- 加密 Excel 只能通过 Excel COM 读取，calamine 无法解密；
- 数据读取后会立即落成 Parquet；
- silver、gold、dashboard 全部从 Parquet/DuckDB 读取，不再读 xlsx。

因此 calamine 降级为可选快速通道：

```python
if 文件未加密:
    使用 calamine 快速读取
else:
    使用 Excel COM 读取
```

建议后续 requirements 将 `python-calamine` 从“必需”改为“可选”；同时新增 `duckdb`、`pyarrow`，Windows 加密环境新增 `pywin32`。

---

### 4. 一次性写入、后续复用：推荐采用

**“处理完只写一次数据库，后续复用，不把读取写入串成每次流水线”是完全正确且更优的设计。**

推荐把链路拆成两个解耦动作：

```text
A. 数据入库（低频，只在换月/源文件变化时执行）
   加密 Excel
     → Excel COM 读一次
     → dtype 标准化
     → raw_YYYYMM.parquet
     → DuckDB 生成/更新分析表

B. 看板与分析（高频，直接复用缓存）
   DuckDB dash_* / gold 表
     → 生成 dashboard_a.html
     → 需要时导出 CSV
```

日常执行方式：

```text
第一次 / 换新数据：
  python run_chain.py --ingest --process --dashboard

以后只是重新出看板：
  python run_chain.py --dashboard-only

以后只是核对结果：
  python run_chain.py --export-csv
```

这样：

- Excel COM 和亿赛通解密每月只发生一次；
- Parquet/DuckDB 读取写入不会反复发生；
- `--dashboard-only` 会非常快；
- 中间表默认不落业务目录，需要时再导出。

---

### 5. 缓存有效性和配置指纹

一次性写入和复用必须配合指纹校验，否则会退回到 P0-1 问题。

建议指纹包含：

```text
源 Excel：路径 + 大小 + mtime + 内容哈希
清洗配置：settings.py / settings_customer.py / settings_product.py
算法版本：processing 代码版本或 git hash
DuckDB schema 版本
```

规则：

| 变化内容 | 需要重做 |
|---|---|
| 源 Excel 变化 | ingest + silver + gold + dashboard |
| 清洗配置变化 | silver + gold + dashboard |
| 评分/规则代码变化 | gold + dashboard |
| 仅模板变化 | dashboard |
| 无变化 | 直接读缓存 |

---

### 6. 目标目录结构

```text
看板流水线/
├─ data/
│  └─ 财务分析-XX.xlsx               # 唯一业务输入
├─ cache/
│  ├─ raw_202606.parquet             # 原始明细缓存
│  └─ analysis.duckdb                # silver/gold/dash 技术表
├─ dashboard/
│  └─ dashboard_a.html               # 唯一正式看板产物
└─ export/                           # 可选，核对/交付时生成
   └─ 202606/
      ├─ gold_*.csv
      └─ 客户分析报告.xlsx
```

原则：

1. `cache/` 是技术缓存，不算业务中间表；
2. `export/` 默认不生成；
3. 看板正式产物只有一个 HTML；
4. 缓存按指纹自动失效重建，对用户透明。

### 7. DuckDB 表设计

只缓存真正会被复用的表：

| 表 | 用途 | 是否长期保留 |
|---|---|---|
| raw_fact | 原始明细 | 是，月度 Parquet 归档 |
| silver_customer_monthly | 客户月聚合 | 是 |
| silver_product_monthly | 产品月聚合 | 是 |
| silver_customer_x_product | 客户×产品×月 | 是 |
| gold_customer | 客户全景 | 是 |
| gold_product | 产品画像 | 是 |
| dash_a / dash_b / ... / dash_f | 看板各面预聚合 | 是 |
| 过程临时表 | 评分、预测、规则中间结果 | 否，用完即删 |

### 8. 新链路预计耗时

| 环节 | 预计耗时 |
|---|---:|
| Excel COM 读取（待实机测试） | 预计 30秒–3分钟 |
| dtype 标准化 + 写 Parquet | 约 1–2秒 |
| DuckDB 生成 silver | 约 0.2–0.5秒 |
| Python 复杂模型/评分/预测 | 约 30–60秒 |
| DuckDB 生成 dash 预聚合表 | 约 1–5秒 |
| HTML 渲染 | 约 5–15秒 |
| 后续 dashboard-only | 约 10–30秒 |

整体目标：首次全量进入 **1.5–4 分钟**，后续只出看板进入 **10–30 秒**。

### 9. 实施顺序

1. 先做 `--ingest`：Excel COM 读取 → dtype 标准化 → Parquet；
2. DuckDB 用 SQL 生成 silver 三张表；
3. 将 dashboard 的逐客户/逐月循环逐步替换为 DuckDB 聚合；
4. 加入缓存指纹和 `--dashboard-only`；
5. 移除 calamine 必需依赖，新增 duckdb/pyarrow/pywin32；
6. 可选 CSV 导出功能独立成 `--export-csv`。
