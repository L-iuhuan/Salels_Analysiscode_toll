## 详细发现

### P0-9-1: 产品→客户分析双向依赖

- **位置**: `product_lifecycle/run.py:32-35`
- **代码**:
  ```python
  from customer_analysis.run_pipeline import (
      calc_customer_portrait,
      generate_gold_tables as generate_customer_gold,
  )
  ```
- **架构图破坏**: 按设计 `product_lifecycle/` 和 `customer_analysis/` 应为并行管道，共享 `shared/` 模块。实际存在产品导入客户的双向依赖
- **隐式排序依赖**: `run_all.py` 先运行产品阶段，再运行客户阶段。但产品阶段内部调用了客户分析函数（用于RFM分群和产品关联分析），这意味着它使用的是来自**之前某次运行**的数据
- **风险**: `calc_customer_portrait` 或 `generate_gold_tables` 签名变更时，`product_lifecycle/run.py` 在表面上正常但功能异常
- **替代方案**: 产品侧的RFM分群和产品关联分析应调用 `shared/customer_analysis.py` 中的共享实现，而非直接调用客户分析管道
- **归因**: B/C — 设计退化，应分离

### P1-9-1: `_derive_channel` 硬编码列名

- **位置**: `customer_analysis/portrait.py:97`
- **代码**: `"代理商/直供名称"`、`"实际终端客户"` 硬编码在函数体内
- **影响**: 如果ERP导出的列名有微小变化（如"代理商/直供名称"变为"代理商_直供名称"），此函数静默返回所有"未知"
- **改进建议**: 将列名移至 `config/settings.py` 的 `CHANNEL_DERIVE` 段
- **归因**: B — 已经在AGENTS.md中被标记为注意事项，但未修复

### P1-9-2: 无统一缺失列错误处理模式

- **问题**: 核心交易列缺失时提供详细中文引导，但客户信息表列缺失时报Python KeyError
- **对比**:
  - 核心列: `run_all.py:110` → `[错误] 缺少必需列: [...] 请检查: 1) ERP_COL_MAP配置... 2) 数据文件列名...`
  - 客户信息表列: `silver.py:70` → Python `KeyError` 回溯（有时被捕获，有时不）
- **影响**: 新部署时用户可能遇到不易理解的Python报错
- **归因**: C — 体验不一致

### P2-9-1: 诊断脚本3处硬编码2026年日期

- **位置**（均在 `output/diagnostic/`）:
  1. `run_quality_analysis.py:78`: `future = (good > "2026-05-24").sum()`
  2. `deep_analysis.py:110-113`: `pd.period_range('2020-01', '2026-04', freq='M')`
  3. `deep_analysis.py:191`: `assert data_min == '2020-01'`
- **影响**: 仅影响诊断报告准确性，不影响生产管道。2026年5月后所有有效数据被标记为"未来"
- **归因**: C — 手工分析脚本未做时间通用化

### P2-9-2: Silver缓存使列变更静默失效

- **位置**: `run_all.py:SKIP_SILVER_IF_EXISTS=True`
- **影响**: 修改 `ERP_COL_MAP` 或新增列映射后，如果不手动删Silver缓存，新配置不生效
- **风险**: 用户在 `settings.py` 中配置了新列映射，感觉"改好了"，但运行结果不变（因为用了旧缓存）
- **归因**: C — 已在AGENTS.md标注但未解决

### P2-9-3: `_L1_TEMPLATES` 建议模板硬编码

- **位置**: `src/actions/rules_engine.py:14-39`
- **影响**: 修改告警建议文字需要改代码，不能通过配置调整
- **建议**: 移至 `config/settings.py` 的 `ACTION_SUGGESTIONS` 段
- **归因**: C — 配置驱动原则不彻底

### P3: 其他发现
- 客户信息表Sheet缺失：`run_all.py:122` 和 `portrait.py:377` 两处读取，异常处理不一致
- `profiling.py:run_profiling()` 接收 `thr` 字典参数而非直接从 `settings.py` 读取 — 优点是可测试，缺点是调用方需知道所有阈值
- `config/settings.py` `SCORE_TIER_THRESHOLDS` 注释标注"上次校准: 2026-05-23" — 阈值可能在数据分布变化后失效

## 数据时间推移兼容性确认

| 年份边缘场景 | 处理方式 | 结果 |
|-------------|---------|------|
| 12月→1月跨年 | `pd.Period` 算术 `month - 12` 自动处理 | ✅ |
| 闰年2月29日 | `pd.to_datetime` 原生支持 | ✅ |
| 数据截至不完整月 | `product_lifecycle/run.py:264-275` 自动检测并排除 | ✅ |
| 客户分析窗口推移 | `CUSTOMER_ANALYSIS_WINDOW.start_date` 在配置中，需手动更新 | ⚠️ 配置提醒 |
| 产品分析起始日期 | `PRODUCT_LIFECYCHE.data_start_date` 在配置中 | ✅ 可更新 |
| 评分阈值校准 | `SCORE_TIER_THRESHOLDS` 基于特定时间段校准 | ⚠️ 需定期重新校准 |

**结论**: 生产代码在时间推移方面是安全的。所有年/月处理使用动态计算。没有发现 `2020-01-01` 过滤范围之外的年边界问题。

## 假想改造评估："销售人员业绩分析"模块

### 假设需求
> 下个月业务方要求增加"销售人员业绩分析"模块——按销售人员维度汇总：销售额、客户数、产品数、拜访频次、新客开发数、回款率。

### 影响分析

| 步骤 | 需要改动的文件 | 改动量 | 阻碍点 |
|------|--------------|--------|--------|
| 1. 销售人员数据已在原始Excel中（有"实际业务员"列） | `config/settings.py` | 无需改动 | ✅ 列已存在 |
| 2. 销售人员数据已在Silver层（`silver_cleaned_rows.csv`有"实际业务员"列） | 无需改动 | 0行 | ✅ 列已自动通过 |
| 3. 编写销售人员聚合计算 | 新建 `salesperson/analysis.py` | ~80-120行 | ⚠️ 需明确聚合口径 |
| 4. 在 `salesperson/` 中定义Gold表生成 | 同文件 | ~30行 | ✅ B2B v2模式可参考 |
| 5. 注册新管道阶段 | `run_all.py` | ~5行 | ✅ 加在stage_map和RUN_STAGES中 |
| 6. 配置阈值和评分参数 | `config/settings.py` | ~15行 | ✅ 现有模式 |
| 7. 生成Excel报告Sheet | `customer_analysis/report.py` | ~10行 | ✅ 自动sheet生成，特殊格式需额外 |

### 估算

| 指标 | 值 |
|------|-----|
| 文件改动数 | **3个现有 + 1个新建** |
| 代码行数 | ~150-180行 |
| 阻碍点 | **无重大阻碍** |
| 总工期 | **1-2天**（含测试） |

### 如果需求更复杂怎么办？

| 变体需求 | 额外影响 | 工期增加 |
|---------|---------|---------|
| 需要**新数据源**（如CRM拜访记录） | 新增数据摄入逻辑，改动`shared/data_cleaning.py` | +1天 |
| 需要**跨模块依赖**（销售人员×产品×客户） | 需确保Silver层包含关联键 | +0.5天 |
| 需要**实时KPI看板** | 需建立或扩展现有KPI通道 | +2-3天 |
| 替换RFM为客户价值模型（如K-Means） | 模块耦合低，替换`models.py`即可 | 不适用于此模块 |

**结论**: 当前架构对新模块扩展友好。核心阻碍点少，约1-2天可完成。
