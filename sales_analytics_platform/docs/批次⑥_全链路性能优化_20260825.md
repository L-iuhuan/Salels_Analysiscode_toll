## 二、等价性验证（全部通过）

**方法论说明（重要）**：批次⑤ 的基线是在"临时 category→object 补丁"下生成的，验证中发现
silver 从 parquet 重载（category dtype）与内存构建（object dtype）会产生若干**预先存在的**
产物差异（categorical groupby 默认 observed=False 叉积：提价机会 8 万行↔246 万行等）。
因此批次⑥ 采用严格 A/B：**同一 silver 来源（parquet/category）、同一输入，HEAD 代码 vs 批次⑥ 代码**。

| 验证项 | 结果 |
|---|---|
| gold 层 28 个 CSV（批次⑥ vs HEAD参照） | **28/28 字节级完全一致** |
| silver 层 4 个 CSV | **4/4 字节级完全一致** |
| 客户分析报告 xlsx（26 sheets 逐格比对） | **26/26 完全一致** |
| 产品生命周期报告 xlsx（7 sheets 逐格比对） | **7/7 完全一致** |
| 看板 46 个数据变量（HEAD vs 批次⑤+⑥，同输入） | **46/46 完全一致** |
| 全链 exit code + 脚本自带审计 | 全部通过 |

## 三、改动清单（9 个文件）

### 1. P3 ETS 客户预测多进程并行（-35s 左右，含于 Gold 表 -50.6s）
- `customer_analysis/trend_analysis.py`：`calc_customer_forecast` 的逐客户 ETS 拟合（1,478 次，
  46.6s）改为"按原 groupby 顺序收集任务 → ProcessPoolExecutor.map 并行（保序返回）→ 按序组装"。
  同一确定性算法、同一输入 → 结果逐位一致；任务 <64 或并行不可用时回退串行（结果相同）。
- `shared/forecasting.py`：新增模块级 worker `ets_forecast_picklable`（Windows spawn 可序列化）。

### 2. P4 gold 子模块向量化（含于 Gold 表 -50.6s）
- `b2b_v2/journey/stage_classifier.py`（37.0s → ~12s）：
  历史阶段判定改数组版（每客户预取 numpy 数组+首个正收入位置，替代 25,609 次
  Series.iloc/.get/掩码扫描+循环内 import）；成熟期修正的近6月营收改为复用主循环已算值
  （原为再跑两遍全表 groupby）；渠道 peers 列表预计算（原为每成熟期客户全表扫描）。
- `b2b_v2/actions/product_insights.py` `build_historical_glory`（20.4s → ~4s）：
  12 月滚动窗口求和改 ndarray 切片（每客户每月一行，窗口=连续切片，同一 np.add.reduce，
  含 NaN 兜底回原路径）；客户×产品查询改一次性 groupby 预分组（替代每客户 151K 行全表扫描）。
- `b2b_v2/actions/cross_sell.py`（17.8s → ~6s）：候选打分循环只算 (dead, score, prod) 轻量元组，
  理由文案只为 top-N 重构；`heapq.nlargest` 替代全量排序（CPython 文档保证与 sorted 等价）；
  产品画像/库龄首匹配映射预构建（替代每产品全表 astype+等值扫描）。
- `customer_analysis/rd_recommendation.py`（14.7s → ~3s）：全公司高质量/总收入占比提升出循环
  （原每产品重算 2 次全表过滤）；yoy6/cxp2 按产品预分组（替代 800×151K 行扫描）。

### 3. P5 节假日比率记忆化（~15-19s，分布于 product/customer）
- `shared/forecasting.py` `calc_monthly_holiday_ratios`：纯函数按 (year, month) 模块级缓存，
  原被调用 1,426 次逐日 is_workday 重复计算同一批月份。

### 4. P2 Excel 导出（customer -7.7s + product ~-5s）
- `reports/gold_exporter.py`：单元格写入按列 dtype 分派——float dtype 列走矢量化快速路径
  （np.round + 掩码 + 极值估列宽），object 列保留与原实现完全一致的逐格 isinstance 分派
  （**关键教训：object 列中的 Python float 在原实现中走 write_number，不能按列 dtype 降级为
  字符串**——首版此处理解错误导致单元格类型变化+耗时反升，已修正并验证 26 sheet 逐格一致）。
- `product_lifecycle/report.py`：6 处 `iterrows` → `itertuples(index=False, name=None)`
  （值序列一致，快 5-10 倍）；逐格新建 Alignment 改为共享实例（值对象，产出 xlsx 一致）。

### 5. 看板残留循环（含于看板 -24s）
- `dashboard/generate_dashboard.py`：YTD/H1 的产品线/品类等值过滤循环（~75 次全表扫描）
  改一次性 groupby 预分组（与批次⑤ P1 同模式、同等价保证）。

### 6. 附带修复（批次⑤ 缺陷A 的遗漏点）
- `reports/gold_exporter.py`：删除两行残留的旧路径常量覆盖（原在 import 之后重新把
  OUTPUT_GOLD/OUTPUT_REPORT 指回 processing/，导致批次⑤ 的路径统一对该文件未生效，
  且 CSV 被双写到两个 output 目录）。

### 7. P6（product 多进程调优）— 评估后放弃
历史画像 ProcessPool 的 17.7s 开销主要是把大 DataFrame pickle 到 worker 的 IPC 成本；
消除需共享内存改造（风险高、收益不确定），按"数字零变化优先"原则放弃，记录在案。

## 四、验证过程中发现的既有问题（非本批次引入，建议另行立项）

1. **silver 来源影响产物**：内存构建（object dtype）与 parquet 重载（category dtype）的
   silver 会产生不同 gold 产物——categorical groupby 默认 observed=False 展开客户×产品
   叉积（提价机会 8 万行↔246 万行、品类标签口径、float32/64 打印格式等）。
   生产环境（CSV/parquet 重载路径）= category 行为。建议统一口径：
   `calc_markup_opportunity` 等处显式 `observed=True`（需业务确认 246 万行是否预期）。
2. **同一份 gold CSV 被 gold.py 与 gold_exporter 双写**（批次⑥ 已随路径统一消除跨目录双写，
   但同目录内仍存在两次写同一文件的浪费，可后续合并写入方）。
3. 看板/前段其余中小循环（A 面 pline/cat、8c 部门等）按最小 diff 原则未动，残留约 20-30s 空间。
