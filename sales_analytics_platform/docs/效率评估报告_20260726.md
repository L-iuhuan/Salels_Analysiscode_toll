## 1. 时间花在哪（实测分解）

```
总耗时 560.4s
├─ 前段·数据处理        287.6s (51%)
│   ├─ silver           31.0s   读219MB Excel(calamine) + 清洗聚合 + 写184MB CSV
│   ├─ product          ~45s    历史画像22.3s + 指标13.1s + 写10.7MB报告
│   ├─ customer        203.5s   ★前段最大头(占全程36%)
│   │   ├─ 客户全景画像  63.4s   (3143个客户)
│   │   ├─ Gold表生成   123.6s   ★全程单点最大头之一
│   │   └─ Excel报告     15.9s
│   └─ kpi + cross_ref   ~8s
└─ 后段·生成看板        272.8s (49%)
    ├─ 读219MB原始Excel  ~90s    openpyxl引擎（calamine只需19.1s）
    ├─ 读184MB silver CSV ~8s
    └─ 6个面计算+C面+HTML ~170s
```

三个最大瓶颈（约占总时长 75%）：
1. 后段 6 个面的**计算** ~170s
2. 前段 customer 的 **Gold表生成+客户画像** = 187s
3. 后段**读原始 Excel 用错引擎** ~90s（可压到 ~19s）

## 2. 数据科学专家视角 —— 根因

- **① 后段读 Excel 用错引擎（实测）**：`generate_dashboard.py` 不指定引擎 → openpyxl = 90.2s；前段 `read_excel_auto` 早已用 calamine = 19.1s（同一文件，4.7x 差距）。
- **② 原始 219MB Excel 被读两遍**：silver 一次（calamine ~19s）+ 后段一次（openpyxl ~90s）。根源：后段没有消费前段算好的 gold 层，而是从 raw 重新推导。
- **③ silver_cleaned_rows.csv(184.5MB) 一写两读**：CSV 文本格式又大又慢还要重新解析类型；Parquet 可缩到 ~1/5–1/10，读快 5-10x。
- **④ customer 阶段 187s 大概率是 Python 层循环**（3143 客户逐个画像/Gold 生成），向量化通常 3-10x，但需保数字逐位不变。
- **⑤ 全程单线程**：后段 6 个面彼此独立，属"尴尬并行"场景却串行。

## 3. 架构师视角 —— 结构性问题

| 结构性问题 | 影响 | 方向 |
|---|---|---|
| 后段绕过 gold 层从 raw 重算 | 重复读219MB+重复计算 | 后段只消费 output/gold + silver |
| 中间结果用 CSV 传递(184MB) | 写读慢、占盘、丢类型 | Parquet/Feather 作为层间交换格式 |
| 6 个面串行计算 | 多核闲置 | 面级 multiprocessing 并行 |
| 无缓存/增量 | --skip-processing 也全量重算后段 | 按输入哈希做增量缓存 |
| 阶段间靠文件序列化接力 | 184MB 写盘再读盘 | 前后段同进程内存传 DataFrame |

## 5. 辩证视角 —— 必须正视的权衡

- **速度 vs 正确性**：数字是逐一对着 GOOD 参考校验过的。任何让数字变了的"优化"都是负优化。S1/S2 属"只快不改数"；S5/S6/S7 必须配回归校验。
- **速度 vs 健壮性**：后段读 raw 虽慢，却能"脱离前段、只靠一个 Excel 独立出看板"。改吃 gold(S7) 更快更优雅，但把后段绑死在前段输出上——耦合度换速度。
- **速度 vs 可维护性**：代码库非本团队原创。并行(S6)、换引擎(S10)、大重构(S8) 都会抬高未来排错难度。
- **值不值得 vs 使用频率**：每月/每周跑一次 → 只做 S1+S2 即可（已完成）；天天跑/交互式反复调 → 再考虑 S3→S5/S6，且先建数字回归基准。

## 6. 项目经理视角 —— 路线图
