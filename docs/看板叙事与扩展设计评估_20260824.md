# 销售经营看板叙事与扩展设计评估

> 日期：2026-08-24  
> 范围：dashboard_a.html（A~F 面）+ 未来新增面  
> 读者：业务/管理层（非程序员），每月刷新  
> 约束：不修改代码/模板；Tauri 壳 `[STAGE]/[n/m]` 进度协议不受影响

---

## 执行摘要

| 议题 | 一句话方案 |
|---|---|
| 1. 每面口径与使用说明 | 在 `processing/config/settings.py`（或独立 `dashboard/faces.yaml`）维护每面的「定义/口径/来源/用法/更新节奏」配置，生成期注入为 `var FACE_META = {...}`；模板在每个面标题旁加一个统一信息图标，点击展开折叠说明面板。 |
| 2. 待办/重点关注事项清单跟踪面 | 新增 **G面「行动清单」**，事项从 `output/gold/异常日志.csv`、`负毛利分析.csv`、`客户组合健康度.csv` 等风险/异常表生成；状态持久化到 `dashboard/action_items.json`（小文件、入版本库）；看板内提供下拉改状态 + 备注的最小交互；月度跑批时自动结转未关闭项、关闭已失效项、新增当期触发项。 |
| 3. 叙事结构统一 | 建议叙事线：**总览 → 异常与风险 → 客户 → 产品 → 销售 → 行动清单**；当前 A→B→C→D→E→F 可微调为 A→G→B→C→D→E→F，把「异常/行动」前置到决策入口，F 面作为 H1 专项保留在原位或并入 A。 |
| 4. 面的插拔与更新节奏 | 建立 `dashboard/faces.yaml` 注册表，记录每面 `enabled`、`cadence`、`owner`；当前单文件模板下，**生成期跳过禁用面的计算与数据注入**是最稳路径（减少生成时间、避免数据残留），模板条件渲染作为补充；按季度/按需展示的面（如 F 面 H1）由 cadence 控制是否参与当月生成。 |

**最需要用户先拍板的设计决策点**：  
> **G面「行动清单」的状态持久化文件是否入版本库、由谁维护。** 这决定了跨月跟踪是否可靠、业务能否自行改状态、以及月度跑批的结转逻辑能否安全执行。建议先拍板「JSON 文件入 Git + 业务在看板内改状态 + 跑批自动结转」。

## 议题 1：每面口径与使用说明

### 1.1 现状评估

当前 `dashboard_a.html` 的 A~F 面只有区块标题，没有统一的面级说明机制。业务用户反馈"看不懂"，原因主要是：

1. **面与面之间缺少"为什么看这一面"的导语**。例如 A 面同时放了 YTD 总览、趋势、分层、散点、客户列表、型号变迁，信息密度高，但没有一句话说明 A 面的定位。
2. **关键口径散落在代码里**。例如 D 面 "Top33 客户（占收入 50%）"、E 面 "首次大量导入 ≥6000 颗"、F 面 "近 12 月 >10 万" 等阈值都埋在 `generate_dashboard.py` 中，业务无法直接看到。
3. **数据来源和更新节奏不一致**。C 面来自 `output/report/产品生命周期报告`，F 面是 H1 半年度，其他面主要来自 Excel/silver，但看板本身没有提示。
4. **没有集中帮助入口**。新增面越多，用户越难快速理解每面用途。

模板结构上是每个面一个 `<div class="tab-content" id="tabX">`，标题多为 `<h3>` 区块标题，适合在**面标题区**统一增加信息入口。

### 1.2 方案

#### 1.2.1 呈现机制：面标题旁信息图标 + 折叠面板

推荐方案：**每个面的第一个区块标题右侧加一个「ⓘ」图标，点击后在该面顶部展开一条浅灰色"口径条"**。理由：

- **上下文最强**：用户当前在看哪一面，说明就在哪一面，不需要跳转。
- **不打断浏览**：默认折叠，需要时才展开。
- **实现轻量**：只需在模板每个 `tab-content` 顶部加一个占位容器，内容由配置注入。
- **不改动 tab 结构**：对 Tauri 进度协议无影响。

不推荐"集中帮助页"作为主机制，因为业务已经处于某一面时，再跳转会打断分析流；集中页可以作为补充（例如放在右上角菜单）。

#### 1.2.2 文案配置化：不入模板，独立配置

文案应放在配置里维护，生成期注入。两种可选位置：

| 方案 | 位置 | 优点 | 缺点 |
|---|---|---|---|
| A | `processing/config/settings.py` 新增 `DASHBOARD_FACE_DOCS` | 与现有配置同文件，团队熟悉 | 配置文件变大，文案多长不合适 |
| B（推荐） | 新建 `sales_analytics_platform/dashboard/faces.yaml` | 文案独立、可读性好、便于非开发审核 | 多一个文件，需纳入指纹/版本管理 |

推荐 **方案 B**，把面的元数据、口径文案、更新节奏、开关统一放在 `dashboard/faces.yaml`，与 `settings.py` 解耦。

#### 1.2.3 配置 schema 草案（YAML）

```yaml
# dashboard/faces.yaml
# 面的元数据、口径说明、开关、更新节奏统一维护

faces:
  A:
    id: A
    name: 总览决策
    enabled: true
    cadence: monthly
    icon: fa-chart-pie
    description: 从 YTD 收入、毛利、ASP 到 KA/AA 客户结构的月度经营总览。
    sections:
      - title: YTD KPI 卡片
        definition: 本年度截至最新数据月的累计收入、毛利、成本、ASP、新品渗透率、KA+AA 收入。
        source: 主交易表（silver_cleaned_rows / 原始 Excel）
        koujing: |
          - 收入 = RMB 未税金额小计（金额列）求和，单位万元。
          - 毛利率 = 毛利 / 收入 × 100%。
          - ASP = 收入 / 发货数量。
          - KA+AA = 终端客户名称_客户类别 包含 "KA" 或 "AA" 的客户。
        usage: 先看总收入和毛利率同比，再判断 KA+AA 占比是否健康。
        update_note: 每月随最新数据刷新。
      - title: KA/AA 客户列表
        definition: 当前 YTD 周期内 KA、AA 层级客户的收入、毛利、ASP、月环比/同比。
        source: 主交易表 + output/gold/客户全景.csv
        koujing: |
          - 月环比 = 最新完整月 vs 上一月。
          - 月同比 = 最新完整月 vs 上年同月（来自客户全景表的 YoY 列）。
          - 新品% = 该客户新品收入 / 该客户总收入。
        usage: 点击客户名可跳转到 B 面查看详情。
        update_note: 每月刷新。

  B:
    id: B
    name: 客户 360
    enabled: true
    cadence: monthly
    icon: fa-users
    description: 以客户为轴心，查看单个客户近 25 个月的收入、利润、品类、品种、新品、风险。
    sections:
      - title: 客户列表
        definition: 全量客户卡片，支持按层级、活跃状态、风险等级筛选。
        source: output/gold/客户全景.csv + output/silver/silver_cleaned_rows.csv（新品明细）
        koujing: |
          - 活跃状态来自客户全景表。
          - 风险等级来自客户全景表综合评估。
        usage: 左侧点选客户，右侧看趋势和品类构成；用于客户拜访前快速备课。
        update_note: 每月刷新。

  C:
    id: C
    name: 产品生命周期
    enabled: true
    cadence: monthly
    icon: fa-cubes-stacked
    description: 从生命周期视角监控产品画像、风险等级、趋势变化。
    sections:
      - title: 产品画像与风险
        definition: 基于产品生命周期报告，展示每个 SKU 的当前画像、综合风险、毛利率、增长率、策略建议。
        source: output/report/产品生命周期报告_v4.0_*.xlsx（3 个 sheet）；缺失时回退 output/gold/gold_product_portrait.csv
        koujing: |
          - 当前画像：导入期 / 成长期 / 成熟期 / 衰退期 / 夕阳期等。
          - 综合风险等级：高 / 中 / 低，基于销量、毛利、客户集中度等规则计算。
          - 近 12 月毛利率%：按销量加权。
        usage: 先关注"高风险"和"衰退/夕阳"产品数量；点击产品可下钻历史画像追踪。
        update_note: 每月刷新，数据月份以报告中的「最新数据月份」为准。

  D:
    id: D
    name: 销售能力
    enabled: true
    cadence: monthly
    icon: fa-user-tie
    description: 以销售员/部门为维度，评估业绩、能力画像、客户覆盖、品类热度。

  E:
    id: E
    name: 月度作战雷达
    enabled: true
    cadence: monthly
    icon: fa-radar
    description: 月度级次的客户势能、量利拆解、首次大量导入、销售员贡献。

  F:
    id: F
    name: H1 汇总
    enabled: true
    cadence: half_year
    icon: fa-calendar-check
    description: 上半年（1-6 月）经营复盘，包括产品线/品类/部门/客户/新品多维对比。
```

生成期把上述配置转成一段 JSON 注入页面：

```javascript
var FACE_META = {
  A: { name: "总览决策", description: "...", sections: [...] },
  B: { ... },
  ...
};
```

前端在每个面顶部渲染一个可折叠的"口径条"：

```html
<!-- 放在每个 tab-content 顶部，由 JS 统一渲染 -->
<div class="face-info-bar" id="faceInfo-A" style="display:none">
  <div style="background:var(--surface-subtle);border:1px solid var(--border);border-radius:8px;padding:12px 16px;margin-bottom:14px">
    <div style="font-weight:600;margin-bottom:6px">A 总览决策 · 口径与使用说明</div>
    <div style="font-size:12px;color:var(--text-secondary);line-height:1.7">...</div>
  </div>
</div>
```

### 1.3 工作量与风险

| 项 | 评估 |
|---|---|
| 工作量 | 小-中。新增 `faces.yaml` 约 0.5 人天；`generate_dashboard.py` 增加读取配置并注入 `FACE_META` 约 0.5 人天；模板加信息图标和折叠面板约 0.5 人天；文案撰写约 1 人天（业务主导）。 |
| 技术风险 | 低。纯展示层改动，不参与计算；不影响 Tauri 进度协议；不影响指纹键（YAML 可纳入指纹，也可以不纳入，因为只是文案）。 |
| 业务风险 | 低。文案若写错只会造成误解，不会导致数据错误。 |
| 依赖 | 需要业务/数据负责人确认每个面的口径文案。 |

### 1.4 建议

1. **采用方案 B**：新建 `dashboard/faces.yaml`，把面元数据、口径、开关、节奏统一管理。
2. **先写 3 个面的完整示例文案**（建议 A/B/C），跑通机制后再补齐 D/E/F。
3. **信息图标统一用 Font Awesome 的 `fa-circle-info`**，与现有图标库一致。
4. **把 `faces.yaml` 纳入版本库**，但不纳入指纹（文案修改不应触发重算）。

## 议题 2：待办/重点关注事项清单跟踪面（G面）

### 2.1 现状评估

当前看板没有"跟踪"语义。`output/gold/` 里已经有大量异常/风险信号，但没有被汇总成可跟踪的待办清单：

- `异常日志.csv`：客户级异常（营收异动、层级变化等）。
- `负毛利分析.csv`：客户×产品级别的负毛利产品清单、损失金额。
- `客户组合健康度.csv`：客户组合的健康/风险维度评分。
- `客户预测.csv`、`交叉销售建议.csv`：可转化为行动建议。

业务需要的是一个**跨月可跟踪的「行动清单」**，而不是当月只看一次的风险报表。

### 2.2 方案

#### 2.2.1 新增 G面「行动清单」

位置：建议放在总览之后（A → G），让用户进入看板后先看到"这个月要处理什么"。

界面构成：

1. **顶部 KPI 卡**：待处理 / 跟进中 / 已关闭 / 本月新增 的数量。
2. **筛选栏**：按来源（异常日志 / 负毛利 / 客户健康度）、等级（高/中/低）、状态、负责人。
3. **事项列表**：每行一个事项，包含：
   - 事项标题（例如"客户 XXX 负毛利产品 5 个，月损失 12 万"）
   - 来源表 + 规则
   - 触发日期/数据月份
   - 建议行动（来自 gold 表的"策略/建议"列）
   - 状态下拉（待处理 / 跟进中 / 已关闭）
   - 备注输入框
   - 负责人

#### 2.2.2 事项从哪些表、哪些行生成

建议分三类来源，每期跑批时自动生成：

| 来源表 | 触发规则 | 生成的事项示例 |
|---|---|---|
| `output/gold/异常日志.csv` | 异常等级 = "高" 或 "中" | "客户 XXX 营收近12月同比下降 81%，连续下滑 3 个月" |
| `output/gold/负毛利分析.csv` | 负毛利产品数 > 0 且 负毛利损失金额 > 阈值（如 1 万元） | "客户 XXX 有 5 个负毛利产品，月损失 11.7 万，建议停供/调价" |
| `output/gold/客户组合健康度.csv` | 任一风险维度占比 > 阈值（如 衰退风险 > 20%） | "客户 XXX 客户组合健康度低，衰退风险占比 30%" |

每个事项需要有一个**稳定 ID**，用于跨月识别。建议 ID 生成规则：

```
{source}:{customer_code}:{rule_signature}:{data_month}
```

例如：
- `neg_margin:CUST001:loss_1171719:202606`
- `anomaly:CUST002:revenue_drop_81pct:202606`

这样跨月跑批时，可以判断同一事项是否已经存在。

#### 2.2.3 状态存哪：建议入版本库的小文件

推荐：`sales_analytics_platform/dashboard/action_items.json`

结构：

```json
{
  "version": "1",
  "last_batch_month": "2026-06",
  "items": [
    {
      "id": "neg_margin:CUST001:loss_1171719:202606",
      "source": "负毛利分析",
      "customer": "CUST001",
      "title": "客户 CUST001 有 4 个负毛利产品，月损失 117.2 万",
      "level": "高",
      "created_month": "2026-06",
      "status": "跟进中",
      "owner": "张三",
      "note": "已与采购沟通，等待降价反馈",
      "trigger_value": 1171719,
      "suggested_action": "停止供应：STI3452HFI 等 4 个产品"
    }
  ]
}
```

**为什么入版本库**：
- 看板是纯 HTML 产物，没有后端数据库。
- 状态需要跨月持久，且需要多人协作（业务改状态、数据团队改规则）。
- JSON 文件足够小（预计每月几十到几百条），入 Git 不会带来体积问题。
- 入版本库后，状态变更可追溯，避免误删。

**人工操作方式（非程序员可用）**：
- 在看板 G 面直接改状态下拉框、填备注、选负责人。
- 改完后点击"保存"，通过浏览器的 `download` 机制把更新后的 `action_items.json` 下载到本地。
- 业务把新文件提交/覆盖到仓库的 `dashboard/action_items.json`。
- 下次跑批时，生成器读取该文件，把业务改过的状态写回新生成的 HTML 中。

这是**最小交互**方案：不依赖后端、不依赖数据库、不破坏现有单文件架构。

#### 2.2.4 与月度跑批的衔接：结转/新增/关闭

每月跑批时，生成器执行以下逻辑：

1. **读取旧清单**：读取 `dashboard/action_items.json` 的现有事项。
2. **生成新候选**：从 gold 异常/风险表按规则生成当期候选事项。
3. **匹配合并**：
   - 若新候选的 ID 已存在：更新 `trigger_value`、`suggested_action`、`data_month`，保留业务填写的 `status`、`owner`、`note`。
   - 若新候选的 ID 不存在：作为"本月新增"加入，状态默认"待处理"。
   - 若旧事项的 ID 在当期没有触发，但状态不是"已关闭"：保留并标记为"历史结转"；如果连续 N 个月未触发，可自动转为"已关闭"（规则可配置）。
4. **自动关闭规则**：
   - 业务手动设为"已关闭"的事项，跨月不再自动重新打开。
   - 连续 3 个月未再触发且状态为"待处理"的事项，可自动关闭（需业务确认该阈值）。
5. **写回文件**：生成新的 `action_items.json`，供业务下次修改。

### 2.3 工作量与风险

| 项 | 评估 |
|---|---|
| 工作量 | 中。G 面前端约 1-2 人天；生成器读取 gold 表并生成事项约 1 人天；状态持久化与合并逻辑约 1 人天；规则阈值与业务确认约 1 人天。 |
| 技术风险 | 中低。新增一个面的计算，但数据源都是现有 gold 表；需确保 ID 生成规则稳定。 |
| 业务风险 | 中。若自动关闭规则太激进，可能漏掉需要长期跟进的事项；需业务确认阈值。 |
| 依赖 | 需要业务确认：事项来源表、触发阈值、自动关闭规则、状态字段含义。 |

### 2.4 建议

1. **先做 MVP**：只接入 `异常日志.csv` 和 `负毛利分析.csv` 两类来源，跑通状态持久化后再扩展。
2. **状态字段保持简单**：待处理 / 跟进中 / 已关闭，不要增加过多状态。
3. **自动关闭阈值先设宽松**：建议连续 3 个月未触发才自动关闭，避免误关。
4. **明确维护责任人**：建议由销售运营或数据分析负责人每月导出/提交 `action_items.json`。

## 议题 3：叙事结构统一

### 3.1 现状评估

当前 tab 顺序是 **A → B → C → D → E → F**：

| 顺序 | 面 | 当前定位 |
|---|---|---|
| 1 | A 总览决策 | YTD 总览、趋势、KA/AA 客户、型号变迁 |
| 2 | B 客户 360 | 单个客户下钻 |
| 3 | C 产品生命周期 | 产品画像、风险、生命周期 |
| 4 | D 销售能力 | 销售员/部门能力评估 |
| 5 | E 月度作战雷达 | 月度级次的客户/产品/销售异动 |
| 6 | F H1 汇总 | 半年度复盘 |

**逻辑断裂点**：

1. **A 面信息过载**：总览里同时放了客户列表、型号变迁，缺少"下一步行动"的引导。
2. **B/C/D/E 的叙事顺序按"维度"而非"决策流"**：客户 → 产品 → 销售 → 月度雷达，业务看完 A 面后，不知道应该先处理风险还是先看客户。
3. **异常/风险信号分散在 C/E/F 中**：没有一个统一的入口告诉用户"这个月要关注什么"。
4. **F 面是 H1 专项，放在最后合理**，但和 A 面的"总览"有一定重复（产品线毛利率、客户毛利率等）。

### 3.2 方案：统一叙事线

建议叙事线：**总览 → 异常与风险 → 客户 → 产品 → 销售 → 行动清单**。

对应的 tab 顺序建议：

| 新顺序 | 面 | 新定位 | 理由 |
|---|---|---|---|
| 1 | A 总览决策 | 经营总览：收入、毛利、ASP、KA+AA、趋势 | 入口，先看大局。 |
| 2 | G 行动清单（新增） | 当月需跟进的风险/异常/待办 | 从总览直接落到"要做什么"。 |
| 3 | B 客户 360 | 客户维度下钻：单个客户历史、品类、风险 | 行动清单中很多事指向客户，下钻到 B 面。 |
| 4 | C 产品生命周期 | 产品维度：画像、风险、生命周期、策略 | 客户问题往往落到产品，继续下钻。 |
| 5 | D 销售能力 | 销售/部门维度：能力、客户覆盖、品类热度 | 产品问题最终由销售执行。 |
| 6 | E 月度作战雷达 | 月度级次的作战视图：量利拆解、首次导入、销售贡献 | 作为月度执行层面的补充。 |
| 7 | F H1 汇总 | 半年度专项复盘 | 保留，但仅在 H1 后重点展示。 |

如果把 F 面视为"阶段性专项"而不是每月必看，也可以考虑：
- **方案 A（推荐）**：A → G → B → C → D → E → F（F 保留，但可通过 cadence 控制是否启用）。
- **方案 B**：A → G → B → C → D → E，F 面在 H1 期间作为 A 面的一个展开区块出现（工作量更大，但叙事更紧凑）。

### 3.3 迁移成本评估

| 成本项 | 评估 |
|---|---|
| 用户习惯 | 中。业务用户已熟悉 A/B/C/D/E/F 的顺序，插入 G 面和调整顺序需要培训和过渡期。 |
| 技术改动 | 低。只需改 `template.html` 的 tab 按钮顺序和 `tab-content` 顺序；`generate_dashboard.py` 的数据注入顺序不变。 |
| 书签/截图 | 低-中。若有用户保存了特定 tab 的截图或文档，顺序变了会找不到。建议在文档中保留旧顺序对照表。 |
| Tauri 进度协议 | 无影响。进度协议是打印语句，与 tab 顺序无关。 |

### 3.4 建议

1. **采用方案 A**：新增 G 面插入 A/B 之间，其他面顺序不变。这是改动最小、叙事提升最大的方案。
2. **不要一次性大调 B/C/D/E 顺序**：当前顺序已被用户接受，大调收益有限、成本较高。
3. **在 A 面顶部增加一句话导语**："本月需关注事项请查看 G 面行动清单"，强化叙事连接。
4. **若后续新增面，统一按叙事线归位**：新增面必须在 `faces.yaml` 中声明位置和叙事角色。

## 议题 4：面的插拔与更新节奏

### 4.1 现状评估

当前所有面（A~F）每月都生成，即使 F 面是 H1 半年度汇总，也每月出现在 tab 上。随着面不断增加：

- **生成时间增加**：每个面都有计算成本，禁用面不应浪费算力。
- **用户认知负担增加**：不需要每月看的面会分散注意力。
- **维护复杂度增加**：新增面需要改模板、改生成器、改进度协议，缺少注册机制。

### 4.2 方案

#### 4.2.1 建立面注册表 `dashboard/faces.yaml`

在议题 1 的 `faces.yaml` 基础上，扩展为面的注册表：

```yaml
# dashboard/faces.yaml
faces:
  A:
    id: A
    name: 总览决策
    enabled: true
    cadence: monthly
    owner: 数据分析组
    compute_stage: "[2/5] YTD KPI..."   # 关联进度协议阶段（可选）
  B:
    id: B
    name: 客户 360
    enabled: true
    cadence: monthly
    owner: 数据分析组
  C:
    id: C
    name: 产品生命周期
    enabled: true
    cadence: monthly
    owner: 产品分析组
  D:
    id: D
    name: 销售能力
    enabled: true
    cadence: monthly
    owner: 销售运营组
  E:
    id: E
    name: 月度作战雷达
    enabled: true
    cadence: monthly
    owner: 数据分析组
  F:
    id: F
    name: H1 汇总
    enabled: true
    cadence: half_year   # 1月-6月数据完整后重点展示
    owner: 数据分析组
  G:
    id: G
    name: 行动清单
    enabled: true
    cadence: monthly
    owner: 销售运营组
```

#### 4.2.2 更新节奏定义

| cadence 值 | 含义 | 示例 |
|---|---|---|
| `monthly` | 每月生成、每月展示 | A/B/C/D/E/G |
| `half_year` | 每年 1-6 月数据完整后生成/重点展示 | F 面 H1 汇总 |
| `quarterly` | 每季度生成/展示 | 未来可加季度复盘面 |
| `on_demand` | 按需手动开启 | 未来专项分析面 |

`cadence` 决定两件事：
1. **是否参与本月生成**：生成器根据 cadence 判断是否执行该面的计算逻辑。
2. **是否在 tab 栏展示**：模板根据 `enabled` 和 cadence 渲染 tab 按钮。

#### 4.2.3 生成期跳过禁用面（推荐主路径）

在当前单文件模板架构下，最稳的改造路径是：**生成器根据 `faces.yaml` 的 `enabled` 和 `cadence` 决定是否执行该面的计算、是否注入该面的数据变量**。

具体做法：

1. **计算阶段**：
   - 读取 `faces.yaml`，得到启用面列表。
   - 对禁用的面，跳过其 Python 计算代码块（例如 F 面在 non-H1 月份跳过）。
   - 对启用的面，正常计算并注入 `js_data`。

2. **模板渲染阶段**：
   - 生成器用启用面列表动态生成 tab 按钮 HTML，替换模板中的固定 tab 栏。
   - 或者保留模板固定结构，但禁用的面注入空数据，前端不渲染其 tab 按钮。

3. **进度协议兼容**：
   - 当前进度协议是固定的 `[1/5]` 到 `[8/8]` 打印。
   - 新增面时，需要把这些阶段与 `faces.yaml` 中的 `compute_stage` 关联，或者保持现有打印不变、仅在内部跳过计算。
   - **建议**：不要删除或重命名现有 `[STAGE]/[n/m]` 行，只在启用面内部执行计算；新增面的进度打印追加到最后，避免 Tauri 壳解析错误。

#### 4.2.4 模板条件渲染（补充路径）

如果某些面的计算无法完全跳过（例如数据被其他面复用），可以采用**模板条件渲染**：

- 注入一个 `ENABLED_FACES = ['A','B','C',...]` 变量。
- 前端 JS 根据 `ENABLED_FACES` 决定显示哪些 tab 按钮和 tab-content。
- 禁用面的数据仍然注入（避免破坏依赖），但不渲染。

**推荐**：主路径用"生成期跳过"，补充路径用"模板条件渲染"处理依赖复杂的面。

### 4.3 工作量与风险

| 项 | 评估 |
|---|---|
| 工作量 | 中。`faces.yaml` 设计与读取约 0.5 人天；生成器按启用面跳过计算约 1-2 人天；动态 tab 栏渲染约 0.5 人天；测试各面启用/禁用组合约 1 人天。 |
| 技术风险 | 中。F 面若被禁用，需确认 A/E 面没有依赖 F 面的数据；G 面新增时也要注意不破坏现有进度协议。 |
| 业务风险 | 低。用户看不到禁用面，不会误操作；但需提前沟通 cadence 规则。 |
| 迁移风险 | 低。可以逐步把现有硬编码面迁移到 `faces.yaml`，先新增 G 面作为试点。 |

### 4.4 建议

1. **先落地 `faces.yaml` 作为注册表**，即使一开始所有面都 `enabled: true`，也为后续插拔打好基础。
2. **F 面 cadence 设为 `half_year`**，在非 H1 重点月份可降低展示权重或跳过生成，减少用户干扰和算力浪费。
3. **新增面必须先在 `faces.yaml` 注册**，否则生成器报错，防止"野生面"堆积。
4. **进度协议兼容原则**：不删除、不重命名现有 `[STAGE]/[n/m]` 行；新增面的进度追加到末尾或复用现有阶段内部打印。
5. **分阶段实施**：
   - 第一阶段：新增 `faces.yaml`，只用于面元数据和口径说明（议题 1）。
   - 第二阶段：用 `faces.yaml` 控制 G 面的启用（议题 2）。
   - 第三阶段：扩展 `enabled`/`cadence` 到 A~F，实现真正的插拔。

## 附录：示例文案（基于 DASHBOARD_FACE_MAP 真实口径）

### A 面「总览决策」口径示例

> **这面看什么**：快速了解公司当月经营大局——赚了多少钱、毛利怎么样、哪些客户贡献最大、趋势是向上还是向下。
>
> **关键口径**：
> - **YTD 收入/毛利**：从本年 1 月到最新数据月的累计值。收入是 RMB 未税金额，毛利是利润列，毛利率 = 毛利 / 收入。
> - **ASP**：平均售价 = 收入 / 发货数量，反映产品均价变化。
> - **KA+AA**：客户层级里包含 "KA" 或 "AA" 的客户，是公司最核心的大客户群。
> - **型号变迁**：近 12 个月 vs 前 12 个月，客户采购品种的变化，只统计单次销量 ≥6000 颗的型号。
>
> **怎么用**：先看顶部 KPI 卡片把握整体；再扫 KA/AA 客户列表找异常客户；最后看趋势图判断增长/毛利是否在预期区间。
>
> **更新节奏**：每月随最新数据刷新。

### B 面「客户 360」口径示例

> **这面看什么**：聚焦单个客户，回答"这个客户最近怎么样、在买什么、有没有风险"。
>
> **关键口径**：
> - **客户列表**：来自 `output/gold/客户全景.csv`，包含层级、活跃状态、风险等级等属性。
> - **近 25 个月趋势**：该客户每月的收入、利润、数量，用于看长期走势。
> - **品类/品种 Top5**：该客户近 12 个月采购金额最高的品类和型号。
> - **新品明细**：来自 `silver_cleaned_rows.csv` 的新品标记列。
>
> **怎么用**：拜访客户前，先在这里看近半年趋势和采购结构；发现某客户风险等级高时，可结合 G 面行动清单跟进。
>
> **更新节奏**：每月刷新。

### C 面「产品生命周期」口径示例

> **这面看什么**：从生命周期视角监控每个 SKU 的健康度——哪些产品在成长、哪些在衰退、哪些需要立即处理。
>
> **关键口径**：
> - **当前画像**：导入期 / 成长期 / 成熟期 / 衰退期 / 夕阳期，由生命周期报告自动判定。
> - **综合风险等级**：高 / 中 / 低，基于销量、毛利率、客户集中度、趋势斜率等计算。
> - **近 12 月毛利率%**：按销量加权平均，避免小单干扰。
> - **数据月份**：以 `output/report/产品生命周期报告_v4.0_*.xlsx` 中的「最新数据月份」为准；若报告缺失，回退到 `gold_product_portrait.csv`（无历史/桑基/月份）。
>
> **怎么用**：先扫顶部 KPI 卡看高风险产品数量；再用筛选器定位"衰退/夕阳"或"高风险"产品；点击产品下钻历史画像追踪。
>
> **更新节奏**：每月刷新。
