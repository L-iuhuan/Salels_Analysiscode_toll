## 详细发现

### P1-7-1: 收入口径漂移 — Product Lifecycle使用`rev_pos`而Customer Analysis使用`rev_sum`

- **定义差异**:
  - `rev_sum`（客户分析）: `Σ(金额)` — 包含正负全部金额（`shared/data_cleaning.py:144,161,185`）
  - `rev_pos`（产品生命周期）: `Σ(金额 WHERE 金额 > 0)` — 仅正金额（`profiling.py:88,95`）
- **代码证据**:
  ```python
  # data_cleaning.py:144 — 客户分析口径
  rev_sum = ("金额", "sum")
  
  # profiling.py:88 — 产品分析口径
  rev_pos = (rev_col, lambda x: x[x > 0].sum())
  ```
- **业务影响**: 同一产品在"近12月销售额"指标上，两套系统可能报告不同数字。存在退货/冲账的月份，客户分析侧的`rev_sum`会低于产品侧的`rev_pos`
- **下游影响**: 
  - 产品九宫格分类和客户评分卡使用了不同的收入值
  - 交叉关联表(`cross_customer_portfolio_health`)中的收入占比可能与其他模块不一致
- **归因**: B（代码逻辑偏差）— 口径差异合理但不一致，应文档化或统一

### P1-7-2: "营收增长率"同比基期漂移

- **产品（profiling.py:438-442）**:
  ```python
  recent_avg = 近12月销售额 / 近12月月数     # 最近12个月的均值
  prior_avg = 前12月销售额 / 前12月月数       # 再往前12个月的均值
  rev_growth = (recent_avg - prior_avg) / prior_avg  # 截断至 [-1.0, 5.0]
  ```
- **客户（portrait.py:178-180）**:
  ```python
  recent_months = min(customer的数据月数, 12)    # 客户可能不足12个月
  prior_months = min(previous数据月数, 12)       # 同上
  rev_growth = (r_avg - p_avg) / p_avg          # 截断至 [-1.0, 5.0]
  ```
- **漂移**: 产品侧固定24月窗口(近12月 vs 前12月)；客户侧动态窗口(数据量不足时自动缩小)
- **业务影响**: 同一个实体的"营收增长率"在产品和客户分析中可能不同，因为窗口不同
- **归因**: B/C — 动态窗口是合理的容错设计，但未在文档中说明口径不一致

### P2-7-1: 负毛利率被静默排除于历史参照基准

- **文件**: `product_lifecycle/profiling.py:479-480`
- **代码**:
  ```python
  monthly_margins = (pm['profit_clip_sum'] / pm['rev_pos'].replace(0, np.nan)).dropna()
  monthly_margins = monthly_margins[monthly_margins > 0]  # 负毛利率被排除！
  ```
- **影响**: 历史P95/P50/P30基准值只基于正毛利率月份计算 → 产品真实历史包含亏损月份时，基准被人为抬高 → "自比健康度"看起来比实际差 → 风险评分偏高
- **量级**: 约5-15%的产品在部分月份有负毛利率（取决于行业），这些月份被排除后，基准可能偏高了3-8个百分点
- **归因**: B（逻辑偏差）— 排除负值是为了避免季节性亏损扭曲基准，但应同时报告"负毛利率月数占比"作为质量标记

### P2-7-2: Winsorization不对称偏置

- **文件**: `config/settings.py:95-111`, `data_cleaning.py:55-85`
- **配置**: 下界-50% vs 上界+75%
- **不对称**: 向下修剪范围(50pp) vs 向上修剪范围(25pp) — 向下是向上的2倍
- **影响**: 毛利率分布被人为向左偏置。对于极端负毛利率的数据点（如-200%），修剪幅度为150个百分点；对于极端正毛利率（如+200%），修剪幅度为125个百分点。不对称修剪导致汇总毛利率系统性偏低。
- **归因**: B/C — 配置值基于业务经验，但不对称的合理性未文档化

### P2-7-3: KPI通道是独立数据路径

- **文件**: `customer_analysis/run_kpi_daily.py`
- **说明**: 第4行注解说"此模块有独立的Excel读取路径和清洗逻辑"
- **问题**: KPI每日表不从Silver层读取，而是重新读取原始Excel并执行独立的清洗逻辑
  - `run_all.py:209` 调用 `stage_kpi()` → `run_kpi_daily.build_kpi()`
  - `run_kpi_daily.py` 有自己的 `load_data()` 函数（约第30-60行），直接解析原始Excel
  - 如果数据清洗逻辑更新（如`ERP_COL_MAP`或winsorization参数变更），KPI通道不会同步更新
- **风险**: 同一批原始数据经两条路径处理后，KPI日表的汇总值可能与Silver→Gold路径的月度汇总不一致
- **归因**: C（架构债）

### P3-7-1: True Profit模块休眠

- **文件**: `config/settings.py:978-1013`
- **注释**: "当前此模块主要用于评分卡中的'效率运营'维度，但因数据不可靠，此模块保留供后续真实成本数据接入后启用"
- **影响**: 18个配置项、35行代码、一个完整计算模块(532行 `src/profitability/true_profit_estimator.py`)，当前管道中基本不使用其输出
- **归因**: C（死代码）

### P3-7-2: 产品数量在管道路径中的不一致

- **Silver** `product_monthly.csv`: 21,452 product-months
- **Gold** `product_portrait.csv`: 794 products
- **差异**: 并非所有在 monthly 表中出现的产品都进入了 portrait
- **原因**: `profiling.py` 中有过滤条件：
  1. `min_record_months`（不足N个月数据的产品排除）
  2. `数据质量标记`过滤（某些标记的产品排除出评分）
  3. 数据不足但仍在Gold表中有NaN行（20.3%仅存在NaN）
- **风险**: 之前轮次报告的20.3%产品无评分正是由此过滤产生
- **归因**: A/B — 过滤合理但应更透明
