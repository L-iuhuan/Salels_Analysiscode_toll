## 详细发现

### P0-8-1: `profiling.py:251` ~900行单线程iterrows循环

- **位置**: `product_lifecycle/profiling.py:251-1156`
- **模式**: `for _, pinfo in valid_prods.iterrows():`
- **规模**: 900+行的循环体，每次迭代执行50+操作：切片、`.loc[]`查询、`.pm.loc[]`子查询、字典构建、`.at[]`回写
- **产品数**: 794个产品 → 794次迭代
- **内部操作包括**:
  - 第267行: `pm.loc[mask, 'qty_sum'].apply(lambda x: x > 0).sum()` — apply(lambda)替代简单位运算
  - 第330-500行: 多种指标计算的掩码/切片/聚合
  - 第880-1062行: `result_df.at[i, "列名"]` 写回同一个DataFrame 
  - 第1024-1048行: 5因子风险评分组合公式
  - 第1100-1150行: 评分卡分级、策略标签生成
- **可向量化程度**: ~60%的循环体逻辑可以向量化（窗口聚合、分组计算、条件打分），剩余40%需逐行处理
- **估计性能提升**: 如果前60%向量化，后40%保持逐行但预过滤，总耗时可从~60s降至~25s（~2.4x提升）
- **归因**: B — 历史上从v2.8增长而来，从未重构为向量化风格

### P1-8-1: 零分块读取，286MB全量加载

- **证据**: `grep chunksize` 全代码库返回0
- **位置**:
  - `product_lifecycle/run.py:1035`: `pd.read_csv(silver_rows_path)` — 286MB文件全量加载
  - `run_all.py:144`: `raw.to_csv(...)` — 同样大小的文件全量写入
- **影响**: 峰值内存使用至少 ~600MB+（原始DataFrame 286MB × 2 + 中间计算）
- **对比**: 客户分析管道跳过此文件，加载3个聚合Silver CSV（小10倍），是正确做法
- **已有防护**: 第773行 `except MemoryError as _e:` — 开发者已知内存溢出
- **归因**: C — 架构设计时未考虑大数据场景

### P1-8-2: `data_cleaning.py:136` `.copy()` 使峰值内存翻倍

- **位置**: `shared/data_cleaning.py:136`
- **代码**: `df = df.copy()` 在 `monthly_aggregate_double_pass()` 开头
- **影响**: 在Silver层构建刚开始就复制了整个原始DataFrame（~337K行，286MB写入前）
  - 内存中同时存在: 原始df + copy的df → ~572MB
  - 加上3个聚合结果DataFrame: ~800MB+ 峰值
- **修复**: 此copy可能是为了防御性地避免SettingWithCopyWarning。可改用 `copy(deep=False)` 或重构避免
- **归因**: B — 过度的防御性编程

### P1-8-3: `run_all.py` 零计时 — 无法定位全管道瓶颈

- **问题**: 产品生命周期和客户分析各自有精细计时，但主入口脚本 `run_all.py` 没有任何计时
- **细节**:
  - 客户分析: 6个计时器（`[时间]客户数据准备+Silver加载`、`[时间]客户全景画像`、`[时间]Gold表生成`、`[时间]Excel报告`、`[时间]客户分析总计`）
  - 产品生命周期: 4个计时器（`[计时]窗口划分+预聚合`、`[计时]P-2预计算`、`[计时]逐个产品指标计算`、`[计时]参照组计算`）
  - `run_all.py`: 调用 `stage_product()`、`stage_customer()`、`stage_kpi()`、`stage_cross_ref()` — 均无计时包裹
- **影响**: 无法回答"整个管道跑一次要多久？哪个阶段最慢？"
- **归因**: C — 主入口遗漏了基础运维能力

### P1-8-4: Silver数据重复写入 — I/O浪费

- **位置**: `run_all.py:144` + `product_lifecycle/run.py:181`
- **代码**:
  - `run_all.py`: `raw.to_csv(silver_cleaned_rows_csv_path, ...)`
  - `product_lifecycle/run.py`: `raw.to_csv(silver_rows_path, ...)` (`silver_rows_path` 指向同一文件)
- **影响**: 每次完整管道运行，286MB文件被完整写入两次 → ~572MB写入I/O
- **场景**: 这是产品生命周期独立运行入口保留的独立写入逻辑。当从 `run_all.py` 运行时，产品阶段内部的写入是多余的
- **归因**: C — 两个入口相互独立导致重复

### P1-8-5: GroupBy循环反模式（6+次）

- **位置**:
  - `src/journey/stage_classifier.py:112,255,266`: `for cid, grp in df.groupby(cust_col):`
  - `src/behavior/volatility.py:165`: `for cid, grp in cust_monthly.groupby(cust_col):`
  - `customer_analysis/trend_analysis.py:58,181,249`: 3个独立函数中的 `groupby("客户编号")` 循环
- **问题**: `for cid, grp in df.groupby(...):` 遍历每个组并顺序处理，而pandas的向量化GroupBy+apply/transform可以同时在所有组上操作
- **影响**: 随着客户数增长（309→1000+），循环时间线性增加，而向量化方法基本持平
- **归因**: B — 代码从原型自然生长，未优化

### P2-8-1: 仅有一个并行区域

- **位置**: `product_lifecycle/run.py:890-908`
- **内容**: `concurrent.futures.ProcessPoolExecutor` 用于历史画像计算，最多4个工作进程
- **问题**: 除此以外，全管道无任何并行
  - 产品生命周期和客户分析是串行的（`run_all.py` 按阶段顺序调用）
  - Silver层构建单线程
  - 各模块内部无多线程/多进程利用
- **可并行化的区域**:
  - 产品画像和客户画像理论上可并行（读取相同Silver数据，独立计算）
  - `cross_reference` 阶段可在前两阶段完成后并行
  - 每月度聚合可在月份维度并行
- **归因**: C — 架构设计时未考虑并行

### P2-8-2: Dtype优化不一致

- **客户分析**（`customer_analysis/run_pipeline.py:72`）: 使用 `SILVER_DTYPE_MAP` 指定列类型，减少内存约40%
- **产品生命周期**（`product_lifecycle/run.py:1035`）: 使用 `pd.read_csv(..., low_memory=False)` — 全量加载无类型优化
- **影响**: 产品侧重新加载Silver数据时多占~40%内存
- **归因**: B — 客户侧优化了但产品侧未同步

### P2-8-3: `shared/timing.py` 死代码

- **位置**: `shared/timing.py`（79行）
- **状态**: 被 `product_lifecycle/run.py:27` import，但 `timing.start()`、`timing.stop()`、`timing.profile()` 在代码库中未被任何地方调用
- **影响**: 79行维护负担，且给人"已有计时系统"的错觉
- **归因**: C — 遗留代码

### P2-8-4: `MemoryError` 已知但未根本解决

- **位置**: `product_lifecycle/profiling.py:773`
- **代码**: `except MemoryError as _e:` — 在iterrows循环的结果合并处捕获
- **问题**: 仅捕获（并静默吞没？），未看到真正的容错逻辑或降级策略
- **归因**: B — 最简异常处理，未从根源解决

### P3-8-1: `apply(lambda x: x > 0)` 冗余

- **位置**: `product_lifecycle/profiling.py:267`
- **代码**: `pm.loc[mask, 'qty_sum'].apply(lambda x: x > 0).sum()`
- **替代**: `(pm.loc[mask, 'qty_sum'] > 0).sum()` — 更快、更短、更清晰
- **另外2处**:
  - `shared/pricing.py:348,705,778`: `.apply(lambda x: x.n)` → `.dt.n`
  - `customer_analysis/run_kpi_daily.py:73`: `.apply(lambda x: x.month == ... and x.year == ...)` → `.dt.month` / `.dt.year`

### P3-8-2: `sort_values` 无稳定排序指定

- **证据**: 28次 `sort_values` 调用，无一处使用 `kind='mergesort'`
- **影响**: 对于部分有序数据，默认的 `quicksort` 可能退化到O(n²)，且不稳定
